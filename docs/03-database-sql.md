# 3. 데이터베이스와 SQL

> 한 줄 요약: 고객의 가치는 고객의 데이터 안에 있다. FDE는 처음 보는 데이터베이스를 빠르게 파악하고, SQL로 직접 꺼내 보고, 느린 이유를 설명할 수 있어야 한다.

## 개념 요약

### SQL 필수 문법

FDE 면접에서 SQL 실기는 자주 나온다. 아래는 손에 익어야 한다.

```sql
-- 조인: 주문과 고객을 묶기
SELECT c.name, COUNT(o.id) AS order_count, SUM(o.amount) AS total
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.created_at >= '2026-01-01'
GROUP BY c.name
HAVING SUM(o.amount) > 100000
ORDER BY total DESC
LIMIT 10;
```

- **조인 종류**: INNER(양쪽에 다 있는 것만), LEFT(왼쪽은 전부), FULL OUTER(양쪽 전부)
- **WHERE와 HAVING**: WHERE는 묶기 전에, HAVING은 묶은 뒤에 걸러 낸다.
- **실행 순서**: FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
- **NULL**: `= NULL` 은 항상 거짓이다. `IS NULL` 을 쓴다. `COUNT(컬럼)` 은 NULL을 세지 않는다.

위 예시에는 함정이 하나 있다. LEFT JOIN을 썼지만 WHERE에서 `o.created_at` 조건을 걸었기 때문에 주문이 없는 고객은 빠진다. 사실상 INNER JOIN이 된다. 주문 없는 고객도 남기려면 조건을 `ON` 절로 옮겨야 한다. 면접에서 자주 묻는 지점이다.

### 윈도 함수

그룹으로 묶되 행을 합치지 않고 계산한다. "각 고객의 최근 주문 1건"처럼 실무에서 매우 자주 쓴다.

```sql
SELECT *
FROM (
  SELECT o.*,
         ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn
  FROM orders o
) t
WHERE rn = 1;
```

`ROW_NUMBER`, `RANK`, `LAG`, `LEAD`, 누적 합계(`SUM() OVER`)를 알아 둔다.

### 인덱스

- 인덱스는 책의 색인과 같다. 전체를 훑지 않고 원하는 행을 찾게 해 준다. 대부분 **B-Tree** 구조다.
- **장점**: 조회가 빨라진다. **단점**: 쓰기가 느려지고 저장 공간을 쓴다.
- **복합 인덱스**는 컬럼 순서가 중요하다. `(a, b)` 인덱스는 `a` 조건이나 `a, b` 조건에는 쓰이지만 `b` 만으로는 쓰이지 않는다.
- **인덱스가 안 쓰이는 경우**: 컬럼에 함수를 씌움(`WHERE DATE(created_at) = ...`), 앞쪽 와일드카드(`LIKE '%abc'`), 형 변환이 일어남, 걸러지는 행이 너무 많음.
- `EXPLAIN` 으로 실행 계획을 본다. 전체 스캔(Seq Scan, Full Table Scan)인지 인덱스 스캔인지 확인한다.

### 트랜잭션과 ACID

- **원자성(Atomicity)**: 전부 되거나 전부 안 되거나
- **일관성(Consistency)**: 제약 조건을 항상 만족
- **격리성(Isolation)**: 동시에 실행돼도 서로 간섭하지 않는 것처럼
- **지속성(Durability)**: 커밋된 것은 사라지지 않음

### 격리 수준

| 수준 | 막는 문제 | 남는 문제 |
| --- | --- | --- |
| Read Uncommitted | 없음 | 더티 리드 |
| Read Committed | 더티 리드 | 반복 불가능한 읽기 |
| Repeatable Read | 반복 불가능한 읽기 | 팬텀 리드(DB마다 다름) |
| Serializable | 전부 | 성능 저하 |

PostgreSQL의 기본은 Read Committed, MySQL(InnoDB)의 기본은 Repeatable Read다.

### 락과 데드락

- 두 트랜잭션이 서로가 잡은 락을 기다리면 **데드락**이 된다. DB가 감지해서 하나를 실패시킨다.
- 예방: 여러 자원을 잠글 때 항상 같은 순서로 잠근다. 트랜잭션을 짧게 유지한다.

### 정규화와 반정규화

- **정규화**: 중복을 없애 데이터가 어긋나지 않게 한다. 쓰기에 유리하다.
- **반정규화**: 조인을 줄이려고 일부러 중복을 둔다. 읽기에 유리하다.
- 고객사의 운영 DB는 정규화되어 있고, 분석용 DB는 반정규화된 경우가 많다.

### RDB와 NoSQL

| 종류 | 예 | 잘 맞는 경우 |
| --- | --- | --- |
| 관계형 | PostgreSQL, MySQL, Oracle, SQL Server | 관계가 뚜렷하고 정합성이 중요 |
| 문서형 | MongoDB, DynamoDB | 구조가 유연하고 키로 조회 |
| 키-값 | Redis | 캐시, 세션, 순위표 |
| 벡터 | pgvector, Pinecone | 임베딩 유사도 검색 |
| 열 지향(DW) | BigQuery, Snowflake, Redshift | 대용량 분석 집계 |

### OLTP와 OLAP

- **OLTP**: 주문 한 건을 빠르게 읽고 쓴다. 행 단위 저장.
- **OLAP**: 수백만 건을 집계한다. 열 단위 저장.
- 운영 DB에 무거운 분석 쿼리를 날리면 서비스가 느려진다. 읽기 전용 복제본이나 데이터 웨어하우스를 쓴다.

## 현장에서 만나는 상황

### 상황 1: 처음 보는 고객 DB를 파악해야 한다

1. 테이블 목록과 행 수를 본다. 큰 테이블이 핵심 테이블이다.
2. 외래 키로 관계를 그린다. 외래 키가 없다면 이름 규칙(`_id`)으로 추정한다.
3. 컬럼별로 NULL 비율, 고유값 개수, 최솟값과 최댓값을 본다.
4. 담당자에게 "이 컬럼은 실제로 어떻게 쓰이나요"를 묻는다. 문서와 실제는 다르다.

### 상황 2: "조회가 너무 느려요"

- **확인 순서**
  1. 어떤 쿼리가 느린가 (슬로 쿼리 로그)
  2. `EXPLAIN ANALYZE` 로 전체 스캔인지, 예상 행 수와 실제 행 수가 크게 다른지 확인
  3. 조건 컬럼에 인덱스가 있는가, 인덱스를 못 쓰게 만드는 표현은 없는가
  4. N+1 문제는 아닌가 (목록 1번 조회 후 각 행마다 추가 조회 N번)
  5. 필요한 컬럼만 가져오는가
- **고객에게 설명하는 말**: "지금은 원하는 자료를 찾으려고 서류철 전체를 처음부터 넘기고 있습니다. 색인을 달아서 바로 찾게 하겠습니다."

### 상황 3: 운영 DB에 접근해야 한다

- **읽기 전용 계정**을 요청한다. 가능하면 복제본에 붙는다.
- 무거운 쿼리는 업무 시간을 피한다. `LIMIT` 을 습관처럼 붙인다.
- 수정이 필요하면 반드시 트랜잭션 안에서, 영향 받는 행 수를 먼저 `SELECT` 로 확인한다.

### 상황 4: 숫자가 안 맞는다

- 조인 때문에 행이 불어났는가 (일대다 관계에서 SUM이 부풀려진다)
- NULL이 집계에서 빠졌는가
- 시간대 기준이 다른가 (UTC와 KST)
- 삭제 표시(soft delete)된 행을 포함했는가

## 면접 예상 질문

### Q. 인덱스는 무엇이고 왜 모든 컬럼에 걸지 않나요?

인덱스는 특정 컬럼의 값을 정렬된 구조로 따로 저장해 조회를 빠르게 하는 자료구조입니다. 하지만 데이터를 쓸 때마다 인덱스도 갱신해야 하므로 쓰기가 느려지고 저장 공간도 차지합니다. 그래서 조회 조건에 자주 쓰이고 값이 다양한 컬럼에 선택적으로 겁니다.

### Q. 쿼리가 느릴 때 어떻게 접근하나요?

먼저 실행 계획을 확인해 전체 스캔이 일어나는지 봅니다. 조건 컬럼에 인덱스가 있는지, 함수나 형 변환 때문에 인덱스를 못 쓰고 있지 않은지 확인합니다. 애플리케이션 쪽에서는 N+1 쿼리가 없는지 봅니다. 그래도 느리면 필요한 데이터만 가져오게 쿼리를 줄이거나 캐시, 집계 테이블을 검토합니다.

### Q. 트랜잭션 격리 수준을 설명해 주세요.

동시에 실행되는 트랜잭션이 서로의 변경을 어디까지 볼 수 있는지를 정하는 설정입니다. 수준이 높을수록 정합성은 좋아지지만 동시 처리 성능은 떨어집니다. Read Committed는 커밋된 데이터만 읽고, Repeatable Read는 트랜잭션 안에서 같은 조회가 같은 결과를 내도록 보장합니다.

### Q. RDB와 NoSQL은 어떻게 선택하나요?

데이터 사이의 관계가 뚜렷하고 정합성이 중요하면 관계형을 씁니다. 구조가 자주 바뀌거나 단순한 키 조회가 대부분이고 수평 확장이 중요하면 NoSQL을 검토합니다. 확신이 없으면 관계형으로 시작하는 편이 안전합니다.

### Q. N+1 문제가 무엇인가요?

목록을 한 번 조회한 뒤 각 항목의 연관 데이터를 가져오려고 항목 수만큼 쿼리를 추가로 실행하는 문제입니다. 조인으로 한 번에 가져오거나 ORM의 미리 가져오기 기능으로 해결합니다.
