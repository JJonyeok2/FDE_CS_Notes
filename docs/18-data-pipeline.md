# 18. 데이터 파이프라인

> 한 줄 요약: [데이터 통합](./04-data-integration)이 "데이터를 옮기고 맞추는 원칙"이었다면, 여기서는 그 일을 매일 자동으로, 믿을 수 있게 돌리는 구조와 도구를 다룬다. AI 기능은 결국 파이프라인이 공급하는 데이터의 품질만큼만 동작한다.

## 개념 요약

### 파이프라인이란

원본에서 데이터를 꺼내 정리하고 목적지에 넣는 일련의 작업을 **자동으로, 정해진 주기나 이벤트에 따라** 실행하는 것이다.

```
원본(ERP, CRM, 로그, 파일, API)
  → 수집(Ingestion)
  → 저장(Raw)
  → 변환(Transform)
  → 제공(Serving): 대시보드, 분석, ML 모델, RAG 색인, 다른 시스템
```

### 저장소의 종류

| 저장소 | 성격 | 예 |
| --- | --- | --- |
| 데이터 웨어하우스 | 정리된 정형 데이터를 SQL로 분석. 스키마를 먼저 정한다 | BigQuery, Snowflake, Redshift |
| 데이터 레이크 | 원본 그대로 무엇이든 싸게 저장. 파일 형태 | S3, GCS, Azure Data Lake 위의 Parquet, JSON |
| 레이크하우스 | 레이크 위에서 웨어하우스처럼 트랜잭션과 스키마 관리 | Delta Lake, Apache Iceberg 테이블 형식, Databricks |
| 데이터 마트 | 특정 부서나 목적에 맞춘 작은 웨어하우스 | 영업 마트, 재무 마트 |

### 계층 구조 (메달리온 아키텍처)

| 계층 | 다른 이름 | 내용 |
| --- | --- | --- |
| Bronze | Raw, 원본 | 받은 그대로. 손대지 않는다. 문제가 생기면 여기서 다시 계산한다 |
| Silver | Staging, 정제 | 형식 통일, 중복 제거, 타입 변환, 코드값 해석, 품질 검사 통과 |
| Gold | Mart, 제공 | 업무 질문에 바로 답하는 집계와 지표. 대시보드와 AI가 읽는 곳 |

원본을 남겨 두는 것이 핵심이다. 변환 로직은 반드시 틀리고 고쳐지기 때문이다.

### 오케스트레이션

여러 작업을 순서와 의존 관계에 맞게 실행하고, 실패하면 재시도하고, 알리는 일이다.

- **DAG**(방향성 비순환 그래프): 작업과 의존 관계를 그래프로 표현한다. A와 B가 끝나야 C를 시작한다.
- **스케줄**: 매일 새벽 2시, 매시간 등 (cron 표현식)
- **이벤트 트리거**: 파일이 도착하면, 원본 테이블이 갱신되면
- **재시도**: 일시적 실패는 자동으로 다시
- **백필**: 과거 기간을 다시 계산
- **알림**: 실패하거나 늦어지면 담당자에게

| 도구 | 특징 |
| --- | --- |
| Apache Airflow | 가장 널리 쓰임. Python으로 DAG 정의. 기업 환경에서 흔히 만남 |
| Dagster | 작업보다 "만들어지는 데이터(asset)" 중심. 계보와 품질 관리가 강함 |
| Prefect | Python 함수에 데코레이터를 붙이는 가벼운 방식 |
| 클라우드 관리형 | AWS Step Functions, Glue, GCP Composer 등 |
| cron + 스크립트 | 작은 규모에서는 충분. 의존 관계와 재시도가 늘면 한계 |

### 변환 도구: dbt

- 변환을 **SQL SELECT문**으로 정의하면, 테이블 생성, 의존 순서, 테스트, 문서화를 처리해 준다.
- 변환 로직이 SQL 파일로 git에 남아 리뷰와 버전 관리가 된다.
- `unique`, `not_null`, 참조 무결성 같은 데이터 테스트를 선언만으로 붙인다.
- 웨어하우스 안에서 변환하는 ELT 방식의 사실상 표준 도구다.

### 대용량 처리

- 데이터가 한 서버의 메모리를 넘으면 **분산 처리**가 필요하다. Apache Spark가 대표적이다.
- 하지만 대부분의 고객 데이터는 생각보다 작다. 수천만 행까지는 웨어하우스 SQL이나 단일 서버(DuckDB, pandas, Polars)로 충분하다. 분산 처리는 운영 비용이 크므로 필요가 확인될 때 쓴다.

### 스트리밍

| 구성 요소 | 역할 | 예 |
| --- | --- | --- |
| 메시지 브로커 | 이벤트를 받아 저장하고 여러 소비자에게 전달 | Apache Kafka, AWS Kinesis, Google Pub/Sub |
| CDC | DB 변경 로그를 읽어 변경 이벤트로 내보냄 | Debezium |
| 스트림 처리 | 흐르는 이벤트를 실시간으로 집계, 변환 | Flink, Spark Structured Streaming |

- Kafka의 핵심 개념: **토픽**(이벤트 종류), **파티션**(병렬 처리 단위, 파티션 안에서만 순서 보장), **컨슈머 그룹**(여럿이 나눠 읽기), **오프셋**(어디까지 읽었나).
- [데이터 통합](./04-data-integration#배치와-스트리밍)에서 말했듯 실시간이 정말 필요한지 먼저 확인한다.

### 파일 형식과 파티셔닝

- **Parquet**: 열 단위 저장, 압축, 타입 보존. 분석에서 CSV보다 훨씬 빠르고 작다.
- **파티셔닝**: 날짜 등으로 폴더나 테이블을 나눈다(`dt=2026-11-21/`). 필요한 기간만 읽어 비용과 시간이 준다.

### 신뢰할 수 있는 파이프라인의 조건

| 조건 | 내용 |
| --- | --- |
| 멱등성 | 다시 돌려도 결과가 같다. 같은 기간을 덮어쓰거나 UPSERT |
| 관측성 | 언제 돌았는지, 몇 건 처리했는지, 얼마나 걸렸는지 보인다 |
| 데이터 품질 검사 | 행 수, NULL 비율, 중복, 값 범위를 자동 검사하고 실패하면 멈춘다 |
| 최신성 감시 | 데이터가 제시간에 들어왔는지 확인한다. 조용히 멈춘 파이프라인이 가장 위험하다 |
| 계보(Lineage) | 이 지표가 어떤 원본에서 어떤 변환을 거쳐 왔는지 추적할 수 있다 |
| 데이터 계약 | 원본 시스템 담당자와 스키마와 의미를 약속하고, 바꿀 때 미리 알린다 |
| 비밀 관리 | 원본 접속 정보를 코드에 넣지 않는다 |

### AI를 위한 파이프라인

AI 기능도 파이프라인이 필요하다.

- **RAG 색인 파이프라인**: 문서 수집 → 파싱 → 청크 → 임베딩 → 벡터 DB. 바뀐 문서만 다시 처리하고, 삭제를 반영한다. ([RAG와 벡터 DB](./15-rag-vector-db#색인-유지))
- **피처 파이프라인**: ML 모델의 입력값(피처)을 계산한다. 학습할 때와 예측할 때 **같은 방식으로** 계산해야 한다. 다르면 운영에서 성능이 떨어진다(training-serving skew). 피처 스토어가 이 문제를 다룬다.
- **학습 파이프라인**: 데이터 준비 → 학습 → 평가 → 모델 등록 → 배포. MLflow 같은 도구로 실험과 모델 버전을 기록한다.
- **LLM 결과 저장 파이프라인**: LLM이 문서를 분류, 요약, 추출한 결과를 테이블로 저장해 다시 분석에 쓴다. 이때 모델 버전과 프롬프트 버전을 함께 저장해야 나중에 결과를 비교할 수 있다.
- **평가 데이터 파이프라인**: 운영 로그에서 실패 사례를 모아 평가 세트로 쌓는다.

## 현장에서 만나는 상황

### 상황 1: "매일 아침 대시보드가 비어 있어요"

- **확인 순서**
  1. 파이프라인이 돌았는가 (오케스트레이터의 실행 기록)
  2. 돌았다면 성공했는가, 몇 건을 처리했는가
  3. 원본 데이터가 제때 들어왔는가 (원본 쪽 배치가 늦었을 수 있다)
  4. 원본 스키마가 바뀌지 않았는가
  5. 대시보드가 보는 테이블과 파이프라인이 쓰는 테이블이 같은가
- **재발 방지**: 최신성 감시 알림, 처리 건수가 평소와 크게 다르면 알림.

### 상황 2: 고객이 Airflow를 쓰고 있고, 우리 작업을 거기 넣어야 한다

- 고객의 기존 DAG 작성 규칙, 배포 방식, 실행 환경(이미지, 패키지 버전)을 먼저 확인한다.
- 우리 작업은 멱등하게 만들고, 실패하면 고객의 기존 알림 체계로 알리게 한다.
- 고객 담당자가 이해하고 운영할 수 있게 단순하게 짠다.

### 상황 3: "작년 숫자도 새 기준으로 다시 계산해 주세요"

- Bronze 계층에 원본이 남아 있으면 변환 로직만 바꿔 백필한다.
- 원본이 없으면 다시 받아야 한다. 그래서 원본을 지우지 않는다.
- 백필은 운영 시스템에 부하를 주므로 업무 시간을 피하고 기간을 나눠 돌린다.

### 상황 4: 작은 데이터인데 Spark와 Kafka를 도입하자고 한다

- 데이터 규모, 지연 요구, 운영 인력을 숫자로 확인한다.
- 대부분은 웨어하우스 SQL과 스케줄러로 충분하다. 단순한 구조가 고객이 오래 운영할 수 있는 구조다.

## 면접 예상 질문

### Q. 데이터 웨어하우스와 데이터 레이크의 차이는 무엇인가요?

웨어하우스는 정리된 정형 데이터를 미리 정한 스키마로 저장해 SQL 분석에 최적화된 저장소이고, 레이크는 원본을 형식에 관계없이 파일로 싸게 저장하고 읽을 때 구조를 해석합니다. 레이크하우스는 레이크 위에 트랜잭션과 스키마 관리를 더해 두 장점을 합치려는 방식입니다.

### Q. 파이프라인을 왜 계층(Bronze, Silver, Gold)으로 나누나요?

원본을 손대지 않고 보존해 두면 변환 로직이 틀렸을 때 언제든 다시 계산할 수 있습니다. 정제 단계와 업무 지표 단계를 나누면 같은 정제 데이터를 여러 용도로 재사용할 수 있고, 문제가 생겼을 때 어느 단계의 문제인지 찾기 쉽습니다.

### Q. Airflow 같은 오케스트레이터는 왜 필요한가요?

작업이 몇 개뿐이면 cron으로 충분하지만, 작업 사이에 의존 관계가 생기고 실패 시 재시도, 과거 기간 재처리, 실패 알림, 실행 기록이 필요해지면 오케스트레이터가 필요합니다. 작업 흐름을 DAG로 정의해 순서와 상태를 한곳에서 관리할 수 있습니다.

### Q. 파이프라인이 조용히 잘못된 데이터를 넣는 것을 어떻게 막나요?

변환 단계마다 행 수, NULL 비율, 중복, 값 범위 같은 품질 검사를 자동으로 넣고, 실패하면 다음 단계로 넘기지 않고 알립니다. 원본 스키마 변화를 감지하고, 데이터가 제시간에 들어왔는지도 감시합니다. 원본 담당자와 데이터 계약을 맺어 변경을 미리 알게 하는 것도 중요합니다.

### Q. Kafka는 언제 쓰나요?

여러 시스템이 같은 이벤트를 실시간에 가깝게 받아야 하거나, 순간적으로 몰리는 대량의 이벤트를 안정적으로 받아 두었다가 처리해야 할 때 씁니다. 지연이 몇 분에서 몇 시간이어도 괜찮다면 배치가 더 단순하고 운영 부담이 적습니다.

### Q. ML에서 training-serving skew는 무엇인가요?

학습할 때와 운영에서 예측할 때 입력값을 계산하는 방식이 달라서 운영 성능이 학습 때보다 떨어지는 문제입니다. 피처 계산 로직을 한곳에 두고 학습과 예측에서 같은 코드를 쓰게 해서 막습니다.
