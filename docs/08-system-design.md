# 8. 시스템 설계 기초

> 한 줄 요약: 시연에서 잘 되던 것이 실제 사용량에서 무너지지 않게 하려면, 병목이 어디에 생기는지와 장애가 났을 때 어떻게 버티는지를 알아야 한다.

## 개념 요약

### 확장

- **수직 확장**: 서버를 더 좋은 것으로 바꾼다. 쉽지만 한계가 있다.
- **수평 확장**: 서버 대수를 늘린다. 서버가 **상태를 갖지 않아야**(stateless) 가능하다. 세션이나 파일을 서버 안에 두면 안 된다.

### 캐시

자주 쓰는 결과를 저장해 두고 다시 쓴다. 가장 효과가 큰 성능 개선 수단이다.

- **어디에**: 브라우저, CDN, 애플리케이션 메모리, Redis, DB
- **캐시 어사이드 패턴**: 캐시에 있으면 그것을 쓰고, 없으면 원본에서 읽어 캐시에 넣는다.
- **TTL**: 유효 시간. 지나면 버린다.
- **어려운 점은 무효화다.** 원본이 바뀌었는데 캐시가 옛 값을 주면 "숫자가 안 맞는다"는 문의가 온다.
- LLM 응용에서는 같은 질문의 응답, 임베딩, 프롬프트 앞부분을 캐시해 비용과 지연을 줄인다.

### 메시지 큐와 비동기 처리

오래 걸리는 일을 요청 처리 흐름에서 떼어 낸다.

- 사용자에게는 "접수했습니다"를 바로 응답하고, 실제 작업은 워커가 큐에서 꺼내 처리한다.
- **효과**: 응답이 빨라진다, 순간적인 폭주를 흡수한다, 실패한 작업만 재시도할 수 있다.
- **대가**: 결과를 나중에 알려 줘야 한다(폴링, 웹훅, 웹소켓), 순서와 중복을 신경 써야 한다.
- 계속 실패하는 메시지는 **데드 레터 큐**로 빼서 전체가 막히지 않게 한다.

### 로드 밸런싱

- 요청을 여러 서버에 나눈다. 방식: 순서대로(라운드 로빈), 연결이 적은 쪽으로.
- **상태 확인**(health check)으로 죽은 서버를 자동으로 뺀다.

### 데이터베이스 확장

- **읽기 복제본**: 읽기를 분산한다. 복제 지연 때문에 방금 쓴 것이 바로 안 보일 수 있다.
- **파티셔닝**: 큰 테이블을 날짜 등 기준으로 나눈다.
- **샤딩**: 데이터를 여러 DB에 나눈다. 복잡해지므로 마지막 수단이다.
- **커넥션 풀**: DB 연결을 미리 만들어 재사용한다. 풀이 고갈되면 요청이 줄줄이 대기한다.

### CAP 정리

네트워크가 끊겼을 때(Partition) **일관성**(모두 같은 값을 본다)과 **가용성**(항상 응답한다) 중 하나를 포기해야 한다.

- 은행 잔고는 일관성을, 좋아요 수는 가용성을 고른다.
- **최종 일관성**: 잠깐은 어긋나도 결국 같아진다.

### 장애 대응 패턴

| 패턴 | 내용 |
| --- | --- |
| 타임아웃 | 무한정 기다리지 않는다. 모든 외부 호출에 설정한다 |
| 재시도 | 일시적 실패는 지수 백오프로 다시 시도한다 |
| 서킷 브레이커 | 계속 실패하는 대상은 호출을 잠시 끊어 장애가 번지는 것을 막는다 |
| 폴백 | 실패 시 대체 응답을 준다 (캐시된 값, 기본값, 더 작은 모델) |
| 레이트 리밋 | 과도한 요청을 제한해 시스템을 지킨다 |
| 벌크헤드 | 자원을 구획으로 나눠 한쪽의 문제가 전체를 삼키지 않게 한다 |

### 관측성

시스템 안에서 무슨 일이 벌어지는지 밖에서 알 수 있어야 한다.

- **로그**: 무슨 일이 있었는가. 구조화된 형식(JSON)으로, 요청 ID를 넣어 한 요청의 흐름을 따라갈 수 있게 한다.
- **지표**: 얼마나 자주, 얼마나 빠르게. 요청 수, 오류율, 응답 시간.
- **트레이스**: 요청 한 건이 어느 구간에서 시간을 썼는가.
- **알림**: 사용자가 알려 주기 전에 먼저 안다.

### 응답 시간은 평균으로 보지 않는다

평균은 느린 요청을 가린다. **백분위수**로 본다. p95가 2초라면 요청의 5%는 2초보다 느리다는 뜻이다. 사용자 불만은 p95, p99에서 나온다.

### SLA, SLO, SLI

- **SLI**: 측정하는 지표 (성공률, 응답 시간)
- **SLO**: 내부 목표 (성공률 99.9%)
- **SLA**: 고객과의 약속. 어기면 보상한다.
- 99.9%는 한 달에 약 43분의 장애를 허용한다는 뜻이다.

### 설계 문제에 접근하는 순서

면접에서 "OO을 설계해 보세요"를 받았을 때의 틀이다.

1. **요구 사항 확인**: 누가, 무엇을, 얼마나 쓰는가. 질문부터 한다.
2. **규모 추정**: 사용자 수, 초당 요청 수, 데이터 크기를 대략 계산한다.
3. **단순한 구성부터**: 클라이언트, 서버, DB를 먼저 그린다.
4. **데이터 모델과 API**를 정한다.
5. **병목을 찾아 보강**: 캐시, 큐, 복제본을 필요한 곳에 넣는다.
6. **실패 상황**: 각 부품이 죽으면 어떻게 되는가.
7. **절충점**을 말한다. 정답은 없고 선택의 이유가 있다.

## 현장에서 만나는 상황

### 상황 1: 시범 운영은 잘 됐는데 전사 확대 후 느려졌다

- **확인 순서**: 응답 시간을 구간별로 나눈다(애플리케이션, DB, 외부 API, LLM). 가장 큰 구간을 찾는다.
- **흔한 원인**: DB 커넥션 풀 고갈, 인덱스 없는 쿼리, 외부 API의 호출 한도, LLM 제공사의 분당 토큰 한도, 동기 방식으로 처리하는 긴 작업.
- 추측으로 고치지 않고 측정한 뒤 고친다.

### 상황 2: 외부 서비스 하나가 죽으니 우리 서비스 전체가 죽었다

- 타임아웃이 없어서 모든 요청이 그 호출에서 대기하다 자원을 다 쓴 것이다.
- 타임아웃과 서킷 브레이커를 넣고, 그 기능만 꺼진 채로 나머지는 동작하게 한다.

### 상황 3: "보고서 생성 버튼을 누르면 화면이 멈춰요"

- 긴 작업을 요청 안에서 동기로 처리하고 있다. 큐로 빼고, 진행 상황을 보여 주고, 끝나면 알린다.
- **고객에게 설명하는 말**: "지금은 보고서가 다 만들어질 때까지 창구에서 기다리게 하는 방식입니다. 접수증을 먼저 드리고 완성되면 알려 드리는 방식으로 바꾸겠습니다."

### 상황 4: 장애가 났는데 고객이 먼저 알았다

- 알림이 없거나 엉뚱한 것을 보고 있었다. 사용자가 겪는 증상(오류율, 응답 시간) 기준으로 알림을 건다.
- 장애 후에는 비난 없는 회고를 쓴다: 무슨 일이 있었나, 왜 늦게 알았나, 무엇을 바꿀 것인가.

## 면접 예상 질문

### Q. 트래픽이 10배로 늘어난다면 어떻게 대응하시겠습니까?

먼저 현재 병목이 어디인지 측정합니다. 애플리케이션 서버는 상태를 갖지 않게 만들어 수평 확장하고, 반복되는 조회는 캐시로 줄이고, DB는 인덱스 점검 후 읽기 복제본을 검토합니다. 오래 걸리는 작업은 큐로 분리합니다. 한 번에 다 하지 않고 병목이 드러나는 순서대로 적용합니다.

### Q. 캐시를 쓸 때 주의할 점은 무엇인가요?

원본이 바뀌었을 때 캐시가 옛 값을 주는 문제가 가장 큽니다. 데이터가 얼마나 오래된 것까지 허용되는지를 먼저 정하고 그에 맞게 유효 시간과 무효화 방식을 정합니다. 또 캐시가 한꺼번에 만료되어 원본에 요청이 몰리는 상황도 대비합니다.

### Q. 메시지 큐는 언제 쓰나요?

작업이 오래 걸려 사용자를 기다리게 할 수 없을 때, 순간적으로 몰리는 요청을 완충해야 할 때, 실패한 작업을 안전하게 재시도해야 할 때 씁니다. 대신 결과 전달 방식과 중복 처리를 따로 설계해야 합니다.

### Q. 장애를 어떻게 감지하고 대응하나요?

사용자가 체감하는 지표인 오류율과 응답 시간에 알림을 걸어 먼저 감지합니다. 장애가 나면 원인 분석보다 복구를 먼저 하고, 최근 변경을 되돌리는 것부터 검토합니다. 복구 후에는 원인과 재발 방지책을 문서로 남깁니다.

### Q. 평균 응답 시간 대신 p95를 보는 이유는 무엇인가요?

평균은 소수의 매우 느린 요청을 가리기 때문입니다. 대부분은 빠르지만 일부 사용자가 매우 느린 경험을 하고 있어도 평균에는 드러나지 않습니다. 백분위수를 보면 느린 쪽 사용자의 경험을 알 수 있습니다.
