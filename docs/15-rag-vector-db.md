# 15. RAG와 벡터 DB 심화

> 한 줄 요약: [LLM 응용](./09-llm-application)에서 RAG의 큰 그림을 봤다면, 여기서는 실제로 품질을 끌어올리는 부품 하나하나를 다룬다. 고객사 문서로 RAG를 만들면 거의 반드시 "검색이 안 된다"는 문제를 만나고, 그 원인은 대부분 이 부품들에 있다.

## 개념 요약

### 전체 구조 다시 보기

```
[색인]
문서 → 파싱 → 정제 → 청크 → (메타데이터 부착) → 임베딩 → 벡터 DB 저장

[질의]
질문 → (질문 변환) → 검색(벡터 + 키워드) → (필터) → 재순위화 → 맥락 조립 → 생성 → 출처 표시
```

괄호 친 단계는 선택이지만, 운영 수준의 RAG에서는 대부분 들어간다.

### 1. 문서 파싱

가장 과소평가되는 단계다. 여기서 텍스트가 깨지면 뒤의 모든 단계가 쓸모없다.

| 문서 | 어려운 점 | 대응 |
| --- | --- | --- |
| PDF | 다단 편집, 머리글과 바닥글, 표가 텍스트로 뒤섞임 | 레이아웃을 인식하는 파서, 표는 따로 추출해 마크다운이나 HTML 표로 |
| 스캔 문서 | 텍스트가 아니라 이미지 | OCR. 정확도를 반드시 표본 검사 |
| HWP, HWPX | 한국 공공기관과 기업에 매우 많음 | 전용 변환기나 PDF로 변환 후 처리 |
| 엑셀 | 셀 구조, 병합 셀, 여러 시트 | 행 단위로 "컬럼명: 값" 형태의 문장으로 바꾸거나 SQL로 따로 다룸 |
| 슬라이드 | 짧은 문장, 도식 | 슬라이드 단위로 묶고 발표자 노트 포함 |
| 이미지, 도면 | 텍스트가 거의 없음 | 멀티모달 모델로 설명문 생성 후 색인 |

**원칙**: 파싱 결과를 사람이 직접 몇 개 열어 본다. 대부분의 품질 문제가 여기서 바로 보인다.

### 2. 청크 나누기

| 방식 | 설명 | 장단점 |
| --- | --- | --- |
| 고정 길이 | 글자나 토큰 수로 자름 | 단순. 문장과 문단 중간이 잘림 |
| 재귀 분할 | 문단 → 문장 → 단어 순으로 경계를 찾아 자름 | 무난한 기본값 |
| 구조 기반 | 제목, 조항, 섹션 단위로 자름 | 규정, 매뉴얼, 계약서에 좋음 |
| 의미 기반 | 임베딩 유사도가 크게 바뀌는 지점에서 자름 | 계산 비용이 듦 |

- **겹침(overlap)**: 앞뒤 청크가 일부 겹치게 해 경계에서 맥락이 끊기는 것을 줄인다.
- **크기**: 정답은 없다. 질문이 구체적인 사실을 묻는다면 작게, 설명을 요구한다면 크게. 평가 세트로 비교해서 정한다.
- **부모-자식 청크**: 검색은 작은 청크로 정확하게 하고, 모델에게는 그 청크가 속한 큰 단위(섹션 전체)를 준다.
- **맥락 덧붙이기**: 청크만 떼어 놓으면 "이 조항"이 무슨 문서의 무슨 조항인지 모른다. 청크 앞에 문서 제목, 섹션 제목, 한두 문장 요약을 붙여서 임베딩하면 검색이 크게 좋아진다.

### 3. 임베딩

- 텍스트를 고정 길이 숫자 벡터로 바꾼다. 의미가 비슷하면 벡터가 가깝다.
- **모델 선택 기준**: 한국어 성능, 차원 수(클수록 저장과 계산 비용 증가), 최대 입력 길이, 비용, 외부 API 사용 가능 여부(폐쇄망이면 직접 돌릴 수 있는 공개 모델).
- 공개 벤치마크(MTEB 등)는 참고만 한다. **고객 문서와 실제 질문**으로 비교하는 것이 정답이다.
- **같은 모델로** 색인과 질의를 해야 한다. 모델을 바꾸면 전체를 다시 임베딩해야 한다.
- 질문과 문서를 다르게 처리하도록 학습된 모델이 있다. 이런 모델은 앞에 붙이는 접두어(query, passage)를 지켜야 성능이 나온다.

### 4. 유사도

| 방식 | 의미 | 메모 |
| --- | --- | --- |
| 코사인 유사도 | 두 벡터의 방향이 얼마나 같은가 | 가장 많이 씀 |
| 내적 | 방향과 크기를 함께 봄 | 벡터를 정규화하면 코사인과 같아짐 |
| 유클리드 거리 | 두 점 사이의 직선 거리 | 작을수록 가까움 |

모델 문서에서 권장하는 방식을 따른다.

### 5. 벡터 DB와 인덱스

수백만 개의 벡터와 질문을 하나씩 다 비교하면 너무 느리다. 그래서 **근사 최근접 탐색(ANN)** 을 쓴다. 정확도를 조금 내주고 속도를 크게 얻는다.

| 인덱스 | 원리 | 특징 |
| --- | --- | --- |
| Flat | 전부 비교 | 정확하지만 느림. 수만 개 이하에서는 충분 |
| HNSW | 여러 층의 그래프를 타고 가까운 점으로 이동 | 빠르고 정확. 메모리를 많이 씀. 가장 흔한 선택 |
| IVF | 벡터를 군집으로 나누고 가까운 군집만 탐색 | 메모리 효율적. 학습 단계 필요 |
| PQ | 벡터를 압축해 저장 | 메모리 크게 절약, 정확도 손실 |

**주요 선택지**

| 종류 | 예 | 잘 맞는 경우 |
| --- | --- | --- |
| 기존 DB의 확장 | PostgreSQL + pgvector | 이미 PostgreSQL을 쓰고, 데이터가 수백만 건 이하이고, 일반 데이터와 함께 조인과 트랜잭션이 필요할 때 |
| 검색 엔진 | Elasticsearch, OpenSearch | 키워드 검색이 이미 있고 하이브리드 검색이 중요할 때 |
| 전용 벡터 DB | Qdrant, Milvus, Weaviate, Pinecone(관리형) | 데이터가 크고 벡터 검색 성능과 필터가 중요할 때 |
| 라이브러리 | FAISS, Chroma | 실험, 프로토타입, 단일 서버 |

FDE 관점의 판단 기준: 고객 환경에 **설치할 수 있는가**(관리형 서비스는 폐쇄망 불가), 고객이 **이미 운영 중인 DB**가 있는가, **누가 운영할 것인가**. 성능보다 운영 가능성이 먼저다.

### 6. 메타데이터와 필터

- 청크마다 문서 ID, 제목, 날짜, 부서, 문서 종류, 버전, **접근 권한**을 함께 저장한다.
- 검색할 때 "2025년 이후", "인사팀 문서만", "이 사용자가 볼 수 있는 문서만"처럼 거른다.
- **권한 필터는 검색 단계에서** 적용한다. 생성 단계에서 거르려 하면 이미 늦다.
- 필터를 먼저 하고 검색하는지(pre-filter), 검색 후 거르는지(post-filter)에 따라 결과 수와 속도가 달라진다. 필터가 강하면 post-filter는 결과가 거의 안 남을 수 있다.

### 7. 하이브리드 검색

- **벡터 검색**은 표현이 달라도 의미가 같으면 찾는다. 대신 제품 코드, 사람 이름, 조항 번호, 약어처럼 **정확한 단어**에 약하다.
- **키워드 검색(BM25)** 은 정확한 단어에 강하다. 대신 표현이 다르면 못 찾는다.
- 둘을 함께 돌리고 결과를 합친다. 순위만으로 합치는 **RRF**(Reciprocal Rank Fusion)가 간단하고 효과적이다.
- 한국어 키워드 검색은 **형태소 분석기**가 필요하다. 조사 때문에 "계약서를"과 "계약서"가 다른 단어로 취급되면 안 된다.

### 8. 질문 변환

사용자의 질문은 검색에 좋은 형태가 아닐 때가 많다.

| 기법 | 내용 |
| --- | --- |
| 질문 재작성 | 대화 맥락을 반영해 독립된 질문으로 바꿈. "그건 언제까지야?" → "연차 신청은 언제까지 해야 하나?" |
| 다중 질문 | 한 질문을 여러 표현으로 바꿔 각각 검색하고 합침 |
| 질문 분해 | 복합 질문을 하위 질문으로 나눔 |
| HyDE | 가상의 답변을 먼저 만들고 그것으로 검색 (답변이 질문보다 문서와 표현이 비슷하므로) |
| 용어 확장 | 사내 약어 사전으로 질문을 확장 |

변환은 LLM 호출을 추가하므로 지연과 비용이 는다. 효과가 확인될 때만 넣는다.

### 9. 재순위화

- 처음에는 넉넉히(예: 50개) 뽑고, **재순위 모델(cross-encoder)** 로 질문과 청크를 쌍으로 다시 채점해 상위 몇 개만 쓴다.
- 임베딩 검색은 질문과 문서를 따로 벡터로 바꿔 비교하지만, 재순위 모델은 둘을 함께 읽고 판단하므로 더 정확하다. 대신 느려서 전체에는 못 쓴다.
- 품질 향상 대비 구현이 쉬운 편이라 먼저 시도할 만하다.

### 10. 맥락 조립과 생성

- 관련도 순으로 넣고, 각 청크에 출처 번호를 붙인다.
- 너무 많이 넣으면 중요한 정보가 묻힌다. 개수보다 질이다.
- 지시: "주어진 문서에 근거해서만 답하라", "근거가 없으면 모른다고 답하라", "답변의 각 문장에 출처 번호를 붙여라".

### RAG의 변형들

| 이름 | 핵심 아이디어 | 언제 |
| --- | --- | --- |
| Agentic RAG | 에이전트가 검색 여부, 검색어, 검색 횟수를 스스로 판단 | 질문이 복잡해 한 번의 검색으로 부족할 때 |
| GraphRAG | 문서에서 개체와 관계를 뽑아 그래프로 만들고 함께 검색 | "A와 관련된 모든 B"처럼 관계를 따라가야 하는 질문 |
| Text-to-SQL | 질문을 SQL로 바꿔 정형 데이터를 조회 | 숫자, 집계, 표 데이터. 벡터 검색으로는 합계를 못 낸다 |
| 멀티모달 RAG | 이미지, 표, 도면까지 검색 | 매뉴얼, 도면, 슬라이드 |

**긴 컨텍스트와 RAG**: 모델이 한 번에 읽을 수 있는 양이 커져도 RAG는 여전히 필요하다. 문서 전체가 수십만 페이지일 수 있고, 매번 다 넣으면 비용과 지연이 크고, 권한 필터와 출처 표시가 어렵기 때문이다. 문서가 작고 고정되어 있다면 통째로 넣는 쪽이 더 단순하고 정확할 수 있다.

### 색인 유지

- 문서는 바뀐다. 추가, 수정, 삭제를 반영해야 한다.
- 문서마다 내용 해시를 저장해 바뀐 문서만 다시 처리한다.
- **삭제 반영**을 잊기 쉽다. 폐기된 규정이 계속 검색되면 위험하다.
- 버전이 여럿인 문서는 최신 것만 검색되게 하거나 날짜를 함께 보여 준다.

### 평가 지표

| 대상 | 지표 | 의미 |
| --- | --- | --- |
| 검색 | Recall@k | 정답 청크가 상위 k개 안에 들어온 비율 |
| 검색 | MRR | 정답이 몇 번째에 처음 나왔는가의 평균 (높을수록 앞쪽) |
| 검색 | nDCG | 순위까지 고려한 관련도 점수 |
| 생성 | 충실성(Faithfulness) | 답변이 주어진 문서에 근거하는가 |
| 생성 | 답변 관련성 | 질문에 실제로 답했는가 |
| 생성 | 정답 일치 | 기대 답과 같은 내용인가 |

검색 지표와 생성 지표를 **따로** 본다. 그래야 어디를 고쳐야 할지 안다. RAGAS 같은 평가 도구가 있지만, 결국 고객의 실제 질문으로 만든 평가 세트가 핵심이다.

## 현장에서 만나는 상황

### 상황 1: "규정집에 분명히 있는 내용인데 못 찾아요"

- **확인 순서**
  1. 해당 문서가 색인되어 있는가
  2. 파싱 결과에 그 내용이 제대로 들어 있는가 (표가 깨졌거나 OCR이 틀렸을 수 있다)
  3. 그 내용이 어느 청크에 들어갔고, 청크만 봐도 의미가 통하는가
  4. 질문과 문서의 용어가 다른가 (사용자는 "육아휴직", 문서는 "육아휴업")
  5. 필터가 너무 강하지 않은가
- **흔한 해결**: 청크에 문서와 섹션 제목 덧붙이기, 하이브리드 검색, 용어 사전으로 질문 확장, 재순위화.

### 상황 2: "답이 맞긴 한데 옛날 규정이에요"

- 문서 버전과 시행일을 메타데이터로 넣고 최신본만 검색하거나 우선시한다.
- 폐기된 문서를 색인에서 지우는 절차를 만든다.
- 답변에 근거 문서의 날짜를 함께 보여 준다.

### 상황 3: "매출 합계가 얼마예요?"에 엉뚱한 답을 한다

- 벡터 검색은 계산을 못 한다. 질문 유형을 나눠서 숫자와 집계 질문은 Text-to-SQL이나 미리 계산한 지표로 보낸다.

### 상황 4: 고객이 "벡터 DB를 새로 도입해야 하나요?"라고 묻는다

- 데이터 규모, 기존 인프라, 운영 인력을 먼저 묻는다.
- 수백만 건 이하이고 PostgreSQL을 이미 쓰고 있다면 pgvector로 시작하는 것을 권한다. 새 시스템을 운영하는 부담이 가장 크다.

### 상황 5: 응답이 느리다

- 구간별로 시간을 잰다: 질문 변환, 임베딩, 검색, 재순위화, 생성.
- 대부분 생성이 가장 길다. 스트리밍으로 체감 시간을 줄이고, 질문 변환처럼 효과가 작은 단계는 뺀다.

## 면접 예상 질문

### Q. 청크 크기는 어떻게 정하나요?

정답은 없고 문서와 질문의 성격에 따라 평가 세트로 비교해서 정합니다. 구체적인 사실을 묻는 질문이 많으면 작게, 맥락 설명이 필요하면 크게 합니다. 작은 청크로 검색하고 모델에게는 상위 섹션 전체를 주는 방식이나, 청크 앞에 문서와 섹션 제목을 붙이는 방식으로 두 장점을 함께 얻을 수 있습니다.

### Q. 벡터 검색만으로 부족한 이유는 무엇인가요?

벡터 검색은 의미가 비슷한 것을 잘 찾지만 제품 코드, 사람 이름, 조항 번호처럼 정확히 일치해야 하는 단어에 약합니다. 그래서 키워드 검색을 함께 돌리고 결과를 합치는 하이브리드 검색을 씁니다. 한국어는 조사 때문에 형태소 분석기를 갖춘 키워드 검색이 필요합니다.

### Q. HNSW는 무엇인가요?

벡터들을 여러 층의 그래프로 연결해 두고, 위층에서 크게 이동하며 대략적인 위치를 찾은 뒤 아래층으로 내려가며 정밀하게 가까운 벡터를 찾는 근사 최근접 탐색 인덱스입니다. 빠르고 정확도가 높아 많이 쓰이지만 메모리를 많이 사용합니다.

### Q. 재순위화는 왜 하나요?

임베딩 검색은 질문과 문서를 각각 벡터로 바꿔 비교하므로 빠르지만 정밀도가 떨어집니다. 재순위 모델은 질문과 문서를 함께 읽고 관련도를 판단해 더 정확하지만 느립니다. 그래서 임베딩 검색으로 후보를 넉넉히 뽑고 재순위 모델로 상위 몇 개를 고르는 두 단계 구조를 씁니다.

### Q. pgvector와 전용 벡터 DB 중 무엇을 고르겠습니까?

이미 PostgreSQL을 운영 중이고 데이터가 수백만 건 이하라면 pgvector를 먼저 고르겠습니다. 운영할 시스템이 늘지 않고, 일반 데이터와 조인과 트랜잭션이 가능하기 때문입니다. 데이터가 매우 크거나 벡터 검색 성능과 복잡한 필터가 핵심이라면 전용 벡터 DB를 검토합니다. 고객 환경에서는 성능보다 누가 운영할 수 있는지가 먼저입니다.

### Q. RAG에서 문서 권한은 어떻게 처리하나요?

색인할 때 청크마다 원본 문서의 접근 권한 정보를 메타데이터로 저장하고, 검색할 때 질문한 사용자의 권한으로 필터를 걸어 볼 수 없는 문서는 아예 후보에서 뺍니다. 생성 단계에서 막으려 하면 이미 모델이 내용을 읽은 뒤라 유출 위험이 있습니다.

### Q. 컨텍스트 윈도가 길어지면 RAG는 필요 없어지나요?

문서가 적고 고정되어 있다면 통째로 넣는 편이 나을 수 있습니다. 하지만 기업 문서는 양이 훨씬 많고 계속 바뀌며, 매번 전부 넣으면 비용과 지연이 커집니다. 또 사용자별 권한 필터와 출처 표시가 필요하므로 검색 단계는 여전히 필요합니다.
