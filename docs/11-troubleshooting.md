# 11. 트러블슈팅 방법론

> 한 줄 요약: FDE는 처음 보는 환경에서 처음 보는 문제를 푸는 사람이다. 지식보다 중요한 것은 모르는 문제를 만났을 때 흔들리지 않고 범위를 좁혀 가는 절차다.

## 개념 요약

### 기본 절차

어떤 문제든 같은 다섯 단계로 접근한다.

1. **재현**: 문제를 내 눈으로 다시 일으킨다.
2. **범위 좁히기**: 어디까지는 정상이고 어디서부터 이상한지 경계를 찾는다.
3. **가설**: 원인 후보를 세우고, 가장 그럴듯하면서 확인하기 쉬운 것부터 줄 세운다.
4. **검증**: 가설 하나를 확인할 실험을 한다. 한 번에 하나만 바꾼다.
5. **기록**: 증상, 원인, 해결, 재발 방지책을 남긴다.

### 1. 재현

- 재현이 안 되면 고쳤는지도 확인할 수 없다.
- 고객에게 묻는 것: **언제부터**, **누가**(모두인가 일부인가), **무엇을 했을 때**, **정확한 오류 메시지나 화면**, **최근 바뀐 것**.
- "안 돼요"는 정보가 아니다. 무엇을 기대했고 실제로 무엇이 일어났는지를 구분해 받는다.
- 가끔 일어나는 문제는 조건을 모은다. 시간대, 사용자, 데이터, 서버 중 무엇과 겹치는지 본다.

### 2. 범위 좁히기

- **경계 찾기**: 요청이 지나가는 경로를 구간으로 나누고, 각 구간의 입구와 출구에서 정상인지 확인한다. 브라우저 → 네트워크 → 로드 밸런서 → 서버 → DB → 외부 API.
- **이분 탐색**: 경로의 중간을 확인해 문제가 앞쪽인지 뒤쪽인지 가른다. 반복하면 빠르게 좁혀진다.
- **비교**: 되는 것과 안 되는 것을 나란히 놓고 차이를 찾는다. 되는 사용자와 안 되는 사용자, 어제와 오늘, 스테이징과 운영.
- **최근 변경 먼저**: 어제까지 되던 것이 오늘 안 된다면 원인은 대부분 그 사이의 변경이다. 배포, 설정, 인증서 만료, 데이터, 외부 서비스 순으로 본다.
- **git bisect**: 어느 커밋부터 깨졌는지 이분 탐색으로 찾는 명령이다.

### 3. 가설

- 가설은 여러 개를 동시에 적는다. 하나만 붙잡으면 확증 편향에 빠진다.
- 확률과 확인 비용을 함께 본다. 가능성이 조금 낮아도 1분 만에 확인할 수 있으면 먼저 확인한다.
- "흔한 원인 목록"을 머릿속에 둔다.

| 증상 | 먼저 의심할 것 |
| --- | --- |
| 갑자기 전부 안 됨 | 배포, 인증서나 토큰 만료, 디스크 가득 참, 외부 서비스 장애 |
| 일부 사용자만 안 됨 | 권한, 데이터 특이값, 브라우저나 네트워크 환경, 특정 서버 |
| 가끔 안 됨 | 타임아웃, 경쟁 상태, 자원 고갈, 서버 여러 대 중 하나 불량 |
| 점점 느려짐 | 메모리 누수, 데이터 증가에 따른 쿼리 저하, 연결 누수 |
| 내 환경에서만 됨 | 환경 변수, 버전 차이, 네트워크 정책, 권한 |
| 숫자가 안 맞음 | 시간대, 중복, 필터 기준, NULL, 캐시 |

### 4. 검증

- **한 번에 하나만 바꾼다.** 두 개를 바꿔서 고쳐지면 무엇이 원인인지 모른다.
- 바꾸기 전에 결과를 예측한다. "이게 원인이면 이렇게 될 것이다." 예측이 틀리면 가설이 틀린 것이다.
- 운영 환경에서는 읽기만 하는 확인부터 한다. 수정은 마지막이다.
- 우회책(재시작, 캐시 삭제)으로 증상이 사라져도 원인을 안 것은 아니다. 고객에게 그 차이를 분명히 말한다.

### 5. 기록

- 증상, 영향 범위, 타임라인, 원인, 조치, 재발 방지책을 남긴다.
- 사람을 탓하지 않고 구조를 본다. "누가 실수했나"가 아니라 "왜 그 실수가 가능했나".
- 같은 문제가 두 번 나오면 문서로, 세 번 나오면 자동화로 만든다.

### 장애 중에는 복구가 먼저

장애가 진행 중이면 순서가 바뀐다.

1. **영향 파악**: 누가, 얼마나 영향을 받는가
2. **복구**: 되돌리기, 기능 끄기, 우회. 원인을 몰라도 먼저 한다
3. **소통**: 고객에게 현재 상황과 다음 소식 시점을 알린다
4. **원인 분석**: 안정된 뒤에
5. **회고와 재발 방지**

### 도구별 확인 지점

| 구간 | 도구 |
| --- | --- |
| 브라우저 | 개발자 도구의 네트워크 탭, 콘솔 |
| 네트워크 | `curl -v`, `dig`, `nc -zv`, `traceroute` |
| 서버 | 애플리케이션 로그, `top`, `df -h`, `journalctl`, `docker logs` |
| DB | 슬로 쿼리 로그, `EXPLAIN ANALYZE`, 락 대기 조회 |
| 코드 | 디버거, 로그 추가, `git log`, `git bisect` |
| 전체 | 요청 ID로 로그를 이어서 추적, 트레이스, 대시보드 |

### AI 도구와 함께 디버깅하기

- 오류 메시지, 관련 코드, 기대 동작과 실제 동작, 이미 확인한 것을 함께 준다. 맥락이 없으면 일반론만 돌아온다.
- AI가 제시한 원인도 가설일 뿐이다. 검증 단계를 건너뛰지 않는다.
- 고객 데이터나 비밀 값을 그대로 붙여 넣지 않는다.

## 현장에서 만나는 상황

### 상황 1: 고객이 "안 돼요"라고만 한다

- 질문 순서: 무엇을 하려고 했는가 → 무엇을 기대했는가 → 실제로 무엇이 보였는가 → 언제부터인가 → 다른 사람도 그런가 → 화면을 보여 줄 수 있는가.
- 가능하면 화면 공유로 직접 본다. 설명보다 정확하다.

### 상황 2: 고객 환경에 직접 접근할 수 없다

- 고객이 대신 실행할 수 있는 **진단 스크립트**를 만들어 준다. 버전, 설정, 연결 확인 결과를 한 번에 모아 파일로 돌려받는다.
- 로그 수집 방법을 미리 합의한다. 개인정보는 가리고 받는다.

### 상황 3: 원인을 끝내 못 찾았다

- 지금까지 확인해서 **배제한 것**을 정리해 공유한다. 그것도 진전이다.
- 다음에 다시 일어났을 때 원인을 잡을 수 있게 로그와 지표를 추가해 둔다.
- 우회책과 그 한계를 설명한다.

### 상황 4: 내가 모르는 기술이 원인이다

- 모른다고 말하고, 언제까지 확인해서 답하겠다고 약속한다.
- 공식 문서, 오류 메시지 원문 검색, 제품 담당 팀 문의 순으로 찾는다.

## 면접 예상 질문

### Q. 한 번도 본 적 없는 문제를 만나면 어떻게 접근하나요?

먼저 문제를 재현하고, 요청 경로를 구간으로 나눠 어디까지 정상인지 경계를 찾습니다. 그다음 원인 후보를 여럿 세워 확인하기 쉬운 것부터 하나씩 검증하고, 한 번에 하나만 바꿉니다. 해결한 뒤에는 원인과 재발 방지책을 기록합니다.

### Q. 운영 중인 서비스에 장애가 났습니다. 무엇부터 하시겠습니까?

원인 분석보다 복구가 먼저입니다. 영향 범위를 파악하고, 최근 배포가 있었다면 되돌리는 것부터 검토합니다. 복구 중에도 고객에게 현재 상황과 다음 소식 시점을 알립니다. 안정된 뒤에 원인을 분석하고 재발 방지책을 정리합니다.

### Q. 재현되지 않는 버그는 어떻게 다루나요?

발생한 사례들의 공통 조건을 모읍니다. 시간대, 사용자, 데이터, 서버 중 무엇이 겹치는지 봅니다. 조건이 안 보이면 다음 발생 때 원인을 잡을 수 있도록 로그와 지표를 보강해 둡니다. 경쟁 상태나 타임아웃처럼 가끔 일어나는 문제의 흔한 원인도 함께 검토합니다.

### Q. 해결하기 어려웠던 문제와 해결 과정을 말해 주세요.

FDE 면접에서 거의 반드시 나오는 질문이다. 아래 "내 프로젝트와의 연결"에 위 다섯 단계 구조로 두 개 이상 준비해 둔다. 특히 **어떻게 범위를 좁혔는지**와 **어떤 가설을 버렸는지**가 들어가야 한다.
