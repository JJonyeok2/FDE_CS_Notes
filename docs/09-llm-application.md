# 9. LLM 응용

> 한 줄 요약: 요즘 FDE 채용의 대부분은 AI 제품을 고객 업무에 붙이는 일이다. "시연에서 되는 것"과 "매일 믿고 쓸 수 있는 것" 사이의 간격을 메우는 지식이 필요하다.

## 개념 요약

### LLM의 기본 동작

- LLM은 입력된 텍스트 다음에 올 **토큰**을 확률적으로 예측한다.
- **토큰**: 모델이 다루는 텍스트 조각. 비용과 한도의 단위다. 한국어는 영어보다 같은 내용에 토큰이 더 든다.
- **컨텍스트 윈도**: 한 번에 넣을 수 있는 토큰의 최대량. 넣을 수 있다고 다 넣으면 비용과 지연이 늘고 정확도가 떨어질 수 있다.
- **온도(temperature)**: 낮으면 일관되고 높으면 다양하다. 추출이나 분류에는 낮게 쓴다.
- **환각**: 그럴듯하지만 사실이 아닌 내용을 만들어 낸다. 모델은 모른다는 사실을 스스로 알지 못할 수 있다.
- **학습 시점 한계**: 그 이후의 정보와 고객 내부 정보는 모른다.

### 모델을 업무에 맞추는 방법

| 방법 | 내용 | 언제 |
| --- | --- | --- |
| 프롬프트 설계 | 지시, 맥락, 예시를 잘 준다 | 항상 먼저 |
| RAG | 관련 문서를 찾아 함께 넣어 준다 | 내부 지식이나 최신 정보가 필요할 때 |
| 도구 사용 | 모델이 함수를 호출하게 한다 | 계산, 조회, 실행이 필요할 때 |
| 파인튜닝 | 모델을 추가 학습시킨다 | 말투나 형식 고정, 앞의 방법으로 안 될 때 |

비용과 유지 부담이 위에서 아래로 갈수록 커진다. 위에서부터 시도한다.

### 프롬프트 설계

- 역할과 목적, 배경 정보, 구체적인 지시, 출력 형식을 분명히 쓴다.
- 좋은 예와 나쁜 예를 보여 준다.
- 복잡한 일은 단계를 나눈다.
- 모르면 모른다고 답하게 명시한다.
- 프롬프트도 코드처럼 **버전 관리**하고, 바꿀 때마다 평가한다.

### 구조화된 출력

프로그램이 결과를 받아 쓰려면 정해진 형식이어야 한다. JSON 스키마를 지정하고, 받은 뒤 반드시 **검증**한다. 형식이 틀리면 재시도한다.

### 임베딩과 벡터 검색

- **임베딩**: 텍스트의 의미를 숫자 벡터로 바꾼 것. 의미가 비슷하면 벡터가 가깝다.
- **벡터 검색**: 질문의 벡터와 가까운 문서 조각을 찾는다. 유사도는 주로 코사인 유사도를 쓴다.
- 데이터가 많으면 근사 최근접 탐색(HNSW 등)으로 속도를 얻는다.

### RAG

> 부품별 심화 내용은 [RAG와 벡터 DB 심화](./15-rag-vector-db)에 있다.

검색 증강 생성. 질문과 관련된 문서를 찾아 프롬프트에 넣어 답하게 한다.

**색인 단계**: 문서 수집 → 텍스트 추출 → 청크로 나누기 → 임베딩 → 벡터 저장소에 저장

**질의 단계**: 질문 임베딩 → 유사한 청크 검색 → (재순위화) → 프롬프트에 넣어 생성 → 출처와 함께 답변

품질을 좌우하는 지점:

- **문서 추출**: PDF의 표, 스캔 문서, 한글(HWP) 파일. 여기서 깨지면 뒤에서 아무리 잘해도 소용없다.
- **청크 나누기**: 너무 작으면 맥락을 잃고 너무 크면 관련 없는 내용이 섞인다. 제목이나 문단 구조를 따라 나누고 조금씩 겹치게 한다.
- **하이브리드 검색**: 벡터 검색은 의미에 강하지만 제품 코드나 고유 명사 같은 정확한 단어에 약하다. 키워드 검색(BM25)과 섞는다.
- **재순위화**: 넉넉히 뽑은 뒤 재순위 모델로 다시 정렬해 상위만 쓴다.
- **메타데이터 필터**: 날짜, 부서, 문서 종류, **접근 권한**으로 거른다.

**RAG가 틀렸을 때 원인을 나눠 보는 법**

| 증상 | 원인이 있는 단계 |
| --- | --- |
| 정답 문서가 색인에 없다 | 수집, 추출 |
| 정답 문서가 있는데 검색되지 않았다 | 청크, 임베딩, 검색 |
| 검색은 됐는데 답이 틀렸다 | 프롬프트, 생성 |
| 문서에 없는 내용을 지어냈다 | 프롬프트(근거 제한 지시), 생성 |

검색 문제인지 생성 문제인지부터 가르는 것이 디버깅의 시작이다.

### 에이전트와 도구 사용

> 워크플로 패턴, 멀티 에이전트, MCP와 A2A는 [Agentic Workflow와 멀티 에이전트](./16-agentic-workflow)에 있다.

- **도구 사용**(함수 호출): 모델에게 쓸 수 있는 함수의 이름, 설명, 인자 형식을 알려 주면 모델이 어떤 함수를 어떤 인자로 부를지 결정해 돌려준다. 실제 실행은 우리 코드가 하고 결과를 다시 모델에게 준다.
- **에이전트**: 목표를 받아 "생각 → 도구 호출 → 결과 확인"을 스스로 반복하는 구조.
- **MCP**: 모델과 외부 도구, 데이터를 연결하는 방식을 표준화한 프로토콜.
- **워크플로와 에이전트**: 순서가 정해진 일은 고정된 흐름(워크플로)이 더 안정적이고 싸다. 경로를 미리 알 수 없는 일에만 에이전트를 쓴다.
- **위험 관리**: 단계가 늘수록 오류가 누적된다. 반복 횟수 상한, 도구 권한 최소화, 되돌릴 수 없는 행동 전의 사람 확인을 둔다.

### 평가

"좋아진 것 같다"로는 운영할 수 없다. 측정해야 한다.

- **평가 세트**: 실제 질문과 기대 답을 모은다. 고객의 실제 질문으로 만든다. 처음에는 수십 개로 충분하다.
- **검색 평가**: 정답 문서가 상위 k개 안에 들어왔는가.
- **생성 평가**: 정확한가, 근거에 충실한가, 질문에 답했는가.
- **평가 방법**: 정답과 비교(가능한 경우), 사람이 채점, LLM이 채점(기준을 명확히 주고 사람 채점과 맞는지 확인).
- 프롬프트나 모델을 바꿀 때마다 돌려 **퇴행**을 잡는다.
- 운영 중에는 사용자 피드백과 실제 로그에서 실패 사례를 모아 평가 세트에 추가한다.

### 비용과 지연

- 비용은 대체로 입력 토큰과 출력 토큰 수에 비례한다. 출력 토큰이 더 비싸다.
- **줄이는 법**: 작은 모델로 충분한 일은 작은 모델로, 프롬프트 캐싱, 불필요한 맥락 제거, 급하지 않은 것은 배치 처리.
- **체감 지연을 줄이는 법**: 스트리밍으로 첫 글자를 빨리 보여 준다, 여러 호출을 병렬로 한다.
- 제공사의 분당 요청 수와 토큰 한도를 확인하고, 429에 대한 재시도와 대기열을 둔다.

### 가드레일

- 입력 검사: 개인정보 가리기, 주제 밖 질문 거르기
- 출력 검사: 형식 검증, 근거 유무 확인, 금지된 내용 차단
- 답할 수 없으면 사람에게 넘기는 경로를 둔다.

## 현장에서 만나는 상황

### 상황 1: "시연 때는 잘 됐는데 실제 문서를 넣으니 엉뚱한 답을 해요"

1. 틀린 사례를 10개 모은다.
2. 각각에 대해 정답 문서가 검색 결과에 있었는지 본다.
3. 없었다면 검색 문제: 추출이 깨졌는가, 청크가 잘못 나뉘었는가, 용어가 달라서 못 찾았는가.
4. 있었다면 생성 문제: 프롬프트, 너무 많은 맥락, 모델의 한계.
5. 고친 뒤 같은 10개와 기존 평가 세트를 다시 돌린다.

- **고객에게 설명하는 말**: "AI가 답을 지어낸 것이 아니라, 답이 들어 있는 문서를 찾지 못했습니다. 사내에서 쓰는 약어가 문서 표현과 달라서 생긴 문제이고, 약어 사전을 반영해 고치겠습니다."

### 상황 2: "AI가 틀린 답을 하면 누가 책임지나요"

- 100% 정확을 약속하지 않는다. 대신 무엇을 하는지 말한다.
- 답변에 **출처**를 붙여 사람이 확인할 수 있게 한다.
- 위험이 큰 결정은 AI가 초안을 만들고 사람이 확정하는 구조로 한다.
- 정확도를 측정한 수치와 측정 방법을 공유한다.

### 상황 3: "비용이 예상보다 훨씬 많이 나와요"

- 요청별 토큰 사용량을 기록하고 있는가부터 확인한다.
- 흔한 원인: 대화 기록을 통째로 매번 다시 보냄, 검색 결과를 너무 많이 넣음, 에이전트가 불필요하게 반복함, 모든 일에 가장 큰 모델을 씀.

### 상황 4: "어떤 업무에 AI를 쓰면 좋을까요"

- 기술이 아니라 업무에서 시작한다. 반복적이고, 양이 많고, 틀려도 사람이 잡을 수 있고, 성공 여부를 판단할 수 있는 일을 고른다.
- 작게 시작해 실제 사용자로 검증하고 넓힌다.
- 규칙으로 풀 수 있는 일은 규칙으로 푼다. LLM이 항상 답은 아니다.

### 상황 5: 외부 모델 API를 쓸 수 없는 고객

- 고객 VPC 안에서 제공되는 모델 서비스, 또는 사내에서 직접 돌리는 공개 모델을 검토한다.
- 성능, 하드웨어 비용, 운영 부담의 절충을 설명한다.

## 면접 예상 질문

### Q. RAG가 무엇이고 왜 쓰나요?

질문과 관련된 문서를 검색해 프롬프트에 함께 넣어 답하게 하는 방식입니다. 모델이 학습하지 않은 내부 지식이나 최신 정보를 활용할 수 있고, 답변의 근거를 제시할 수 있어 환각을 줄이고 검증을 가능하게 합니다. 파인튜닝과 달리 문서만 갱신하면 되므로 유지가 쉽습니다.

### Q. RAG의 답변 품질이 낮을 때 어떻게 개선하나요?

먼저 실패 사례를 모아 검색 문제인지 생성 문제인지 나눕니다. 정답 문서가 검색되지 않았다면 문서 추출, 청크 방식, 하이브리드 검색, 재순위화를 점검합니다. 검색은 됐는데 답이 틀렸다면 프롬프트와 맥락의 양을 조정합니다. 변경할 때마다 평가 세트로 효과를 확인합니다.

### Q. 환각은 어떻게 줄이나요?

근거가 되는 문서를 제공하고 그 안에서만 답하도록 지시하며, 근거가 없으면 모른다고 답하게 합니다. 답변에 출처를 붙여 검증할 수 있게 하고, 출력에 대해 근거 일치 여부를 검사합니다. 완전히 없앨 수는 없으므로 위험이 큰 업무에는 사람의 확인 단계를 둡니다.

### Q. 파인튜닝과 RAG는 어떻게 선택하나요?

지식을 넣는 것이 목적이면 RAG가 먼저입니다. 지식이 바뀌어도 문서만 갱신하면 되고 출처도 제시할 수 있습니다. 파인튜닝은 특정 말투나 출력 형식을 일관되게 맞추거나, 프롬프트만으로 해결되지 않는 특정 작업의 성능을 높일 때 검토합니다. 둘은 함께 쓸 수도 있습니다.

### Q. LLM 기능의 품질을 어떻게 평가하나요?

실제 사용 사례에서 질문과 기대 답으로 구성된 평가 세트를 만들고, 변경할 때마다 돌려 수치로 비교합니다. 정답 비교가 어려운 경우 명확한 채점 기준을 두고 사람이나 LLM으로 채점하되, LLM 채점은 사람 채점과 일치하는지 확인합니다. 운영 중 발견된 실패 사례를 계속 추가합니다.

### Q. 에이전트는 언제 쓰고 언제 쓰지 않나요?

처리 경로를 미리 정할 수 없고 상황에 따라 다음 행동을 판단해야 하는 일에 씁니다. 순서가 정해진 일은 고정된 워크플로가 더 예측 가능하고 비용도 적게 듭니다. 에이전트는 단계가 늘수록 오류가 누적되므로 가장 단순한 구조로 시작해 필요할 때만 자율성을 늘립니다.
