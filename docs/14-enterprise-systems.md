# 14. 기업 업무 시스템: ERP, CRM, 그룹웨어

> 한 줄 요약: 고객사의 데이터와 업무는 대부분 이미 있는 업무 시스템 안에 있다. FDE가 만드는 것은 새 시스템이 아니라 이 시스템들 위에 얹히거나 사이를 잇는 것이다. 각 시스템이 무엇을 담고 있고 어떻게 연동되는지 알아야 한다.

## 개념 요약

### 한눈에 보기

| 시스템 | 한 줄 정의 | 주로 쓰는 부서 | 담고 있는 데이터 |
| --- | --- | --- | --- |
| ERP | 회사의 돈, 물건, 사람의 흐름을 한 장부로 관리 | 재무, 회계, 구매, 생산, 인사 | 전표, 거래처, 품목, 재고, 주문, 급여 |
| CRM | 고객과의 모든 접점을 관리 | 영업, 마케팅, 고객 지원 | 고객, 영업 기회, 상담 이력, 캠페인 |
| 그룹웨어 | 사내 협업과 결재 | 전 직원 | 전자결재, 메일, 일정, 게시판, 문서 |
| HRIS | 인사 정보 관리 (ERP의 일부이기도 함) | 인사 | 조직, 직원, 근태, 평가 |
| SCM | 공급망 관리 | 구매, 물류 | 공급사, 발주, 재고 이동, 배송 |
| MES | 공장 생산 현장 관리 | 생산 | 작업 지시, 설비, 공정 실적, 불량 |
| ITSM | IT 요청과 장애 관리 | IT 부서 | 요청 티켓, 장애, 자산 |

### ERP

**전사적 자원 관리.** 부서마다 따로 쓰던 장부를 하나로 합친 시스템이다. 영업이 주문을 넣으면 재고가 빠지고, 출고되면 매출이 잡히고, 회계 전표가 자동으로 생긴다.

- **핵심 개념**
  - **마스터 데이터**: 잘 바뀌지 않는 기준 정보. 거래처, 품목, 계정과목, 조직, 직원.
  - **트랜잭션 데이터**: 매일 생기는 거래. 주문, 입출고, 전표, 결재.
  - **모듈**: 재무회계(FI), 관리회계(CO), 영업(SD), 구매(MM), 생산(PP), 인사(HR) 등. 이름은 SAP식이지만 다른 ERP도 비슷하게 나뉜다.
  - **전표**: 회계 기록의 단위. 차변과 대변의 합이 항상 같아야 한다.
  - **마감**: 월말과 연말에 숫자를 확정하는 작업. 마감 기간에는 고객 담당자가 가장 바쁘고, 시스템 변경을 꺼린다.
- **대표 제품**
  - 해외: SAP S/4HANA, Oracle NetSuite와 Fusion, Microsoft Dynamics 365
  - 국내: 더존비즈온(중소, 중견 기업에 많음), 영림원소프트랩, 자체 개발 ERP
- **FDE가 알아야 할 특징**
  - 회사마다 **커스터마이징**이 많다. 같은 제품이라도 회사마다 테이블과 업무 흐름이 다르다.
  - 데이터 정합성이 생명이다. ERP 데이터를 직접 수정하는 일은 거의 허용되지 않는다.
  - 오래된 ERP는 API가 없거나 빈약하다. DB 조회, 파일 연계, 인터페이스 테이블이 흔하다.
  - SAP는 BAPI, RFC, IDoc, OData 같은 고유 연동 방식이 있다. 이름 정도는 알아 둔다.

### CRM

**고객 관계 관리.** 잠재 고객이 들어와서 계약하고, 이후 지원받고, 재구매하거나 떠나는 전체 과정을 관리한다.

- **영업 흐름(파이프라인)**: 리드(잠재 고객) → 검증된 리드 → 영업 기회 → 제안 → 협상 → 계약 성사 또는 실패
- **핵심 객체**: 고객사(Account), 담당자(Contact), 리드(Lead), 영업 기회(Opportunity), 활동(Activity), 케이스(Case, 문의나 불만)
- **세 가지 영역**: 영업 자동화, 마케팅 자동화(캠페인, 이메일), 고객 서비스(상담, 티켓)
- **대표 제품**: Salesforce, HubSpot, Microsoft Dynamics 365, Zendesk(고객 지원 중심), 국내에서는 채널톡 같은 고객 상담 도구도 많이 쓴다.
- **주요 지표**
  - **전환율**: 단계별로 다음 단계로 넘어가는 비율
  - **이탈률(Churn)**: 일정 기간 동안 떠난 고객의 비율
  - **고객 생애 가치(LTV)**: 한 고객이 관계 동안 가져다주는 총 가치
  - **고객 획득 비용(CAC)**: 고객 한 명을 데려오는 데 든 비용
- **AI와 만나는 지점**: 이탈 예측, 리드 점수 매기기, 상담 내용 요약, 다음 행동 추천, 이메일 초안 작성.

### 그룹웨어

**사내 협업 도구 묶음.** 한국 기업에서 특히 중요하다. 업무가 **전자결재**를 중심으로 돌아가기 때문이다.

- **주요 기능**: 전자결재, 메일, 일정, 게시판, 주소록, 문서함, 근태, 메신저
- **전자결재**
  - 기안 → 결재(순차 또는 병렬) → 합의 → 전결 → 시행
  - **결재선**: 누구를 거쳐 승인받는지. 직급과 금액에 따라 달라진다.
  - **양식**: 품의서, 지출결의서, 휴가신청서 등. 회사마다 양식이 수십~수백 개다.
  - 결재가 끝나면 ERP로 데이터가 넘어가는 경우가 많다. 지출결의가 승인되면 ERP에 전표가 생기는 식이다.
- **대표 제품**: 국내는 다우오피스, 하이웍스, 네이버웍스, 카카오워크, 비즈플레이(경비 관리) 등 매우 다양하다. 해외 기업은 Microsoft 365, Google Workspace, Slack, Notion 조합을 많이 쓴다.
- **AI와 만나는 지점**: 결재 문서 요약, 양식 자동 작성, 사내 규정 질의응답, 회의록 정리, 메일 초안.

### 시스템 사이의 연결

실제 회사에서는 이 시스템들이 서로 데이터를 주고받는다.

```
CRM: 영업 기회 성사
  → ERP: 수주 등록 → 출고 → 매출 전표
그룹웨어: 지출결의 승인
  → ERP: 비용 전표
HRIS: 입사자 등록
  → 그룹웨어 계정 생성, 결재선 갱신, ERP 사원 정보
```

어느 시스템이 **원본(System of Record)** 인지 정하는 것이 중요하다. 고객 정보의 원본이 CRM인지 ERP인지 정해지지 않으면 두 곳의 값이 어긋난다.

### 연동 방식

| 방식 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| 공식 API | 제품이 제공하는 REST, SOAP 등 | 안정적, 권한 통제 | 기능이 제한적일 수 있음, 호출 한도 |
| 웹훅 | 일이 생기면 알림 | 실시간 | 지원하지 않는 제품이 많음 |
| DB 직접 조회 | 읽기 전용 계정으로 조회 | 데이터가 풍부 | 스키마가 바뀌면 깨짐, 업데이트가 생기면 지원받기 어려움 |
| 인터페이스 테이블 | 양쪽이 약속한 중간 테이블에 쓰고 읽음 | 한국 기업 SI에서 흔하고 이해하기 쉬움 | 처리 상태 관리가 필요 |
| 파일 연계 | 정해진 시간에 CSV나 엑셀을 주고받음 | 어디서나 가능 | 지연, 형식 깨짐 |
| iPaaS | Zapier, Make, n8n, MuleSoft 같은 연동 플랫폼 | 빠르게 구축 | 복잡한 로직과 대량 처리에 한계, 비용 |
| RPA | 화면을 자동으로 조작 | API가 없어도 가능 | 화면이 바뀌면 깨짐. 마지막 수단 |

**원칙**: 업무 시스템에 **쓰는** 연동은 읽는 연동보다 훨씬 위험하다. 먼저 읽기 전용으로 가치를 증명하고, 쓰기는 사람의 승인을 거치게 한다.

## 현장에서 만나는 상황

### 상황 1: "ERP 데이터로 AI 분석을 하고 싶어요"

1. 어떤 질문에 답하고 싶은지부터 정한다. "재고 회전율이 낮은 품목은?" 같은 구체적인 질문.
2. 그 질문에 필요한 테이블을 ERP 담당자와 함께 찾는다. 테이블과 컬럼 이름이 약어나 코드인 경우가 많다(`MATNR`, `CUST_CD`).
3. **코드값 사전**을 받는다. 상태 코드 `10`, `20`, `90`이 무엇을 뜻하는지 모르면 분석이 틀린다.
4. 운영 DB가 아니라 복제본이나 분석용 DB에서 읽는다.
5. ERP 화면의 숫자와 내가 뽑은 숫자를 대조해 검증한다.

### 상황 2: "CRM에 고객 상담 요약을 자동으로 넣어 주세요"

- CRM의 API로 활동이나 케이스에 메모를 추가하는 기능이 있는지 확인한다.
- 처음에는 요약을 **초안**으로 넣고 상담원이 확인 후 저장하게 한다.
- 고객 개인정보가 외부 모델로 나가는 것에 대해 보안팀과 먼저 합의한다.
- API 호출 한도와 필드 길이 제한을 확인한다.

### 상황 3: "결재 문서를 AI가 써 주면 좋겠어요"

- 자주 쓰는 양식 상위 몇 개부터 시작한다. 전부 하려 하지 않는다.
- 그룹웨어가 양식 작성 API를 제공하는지 확인한다. 없으면 초안을 만들어 복사해 붙이게 하는 것부터 시작한다.
- 사내 규정(경비 한도, 결재 기준) 문서를 함께 RAG로 넣으면 "이 지출은 누구 결재가 필요한가"에도 답할 수 있다.

### 상황 4: 두 시스템의 고객 수가 다르다

- 원본 시스템이 어디인지 확인한다.
- 매칭 키가 무엇인지(사업자등록번호, 고객 코드) 확인하고, 한쪽에만 있는 고객 목록을 뽑아 담당자와 함께 본다.
- [데이터 통합](./04-data-integration)의 엔티티 매칭 방법을 쓴다.

### 상황 5: 고객 담당자가 "그 시스템은 손대면 안 돼요"라고 한다

- 정당한 걱정이다. ERP 장애는 회사 전체를 멈춘다.
- 읽기 전용, 업무 시간 외 실행, 변경 전 승인 절차, 되돌리는 방법을 먼저 제시한다.

## 면접 예상 질문

### Q. ERP, CRM, 그룹웨어의 차이를 설명해 주세요.

ERP는 회계, 구매, 재고, 인사처럼 회사 내부 자원의 흐름을 하나의 장부로 관리하는 시스템이고, CRM은 잠재 고객부터 계약, 지원까지 고객과의 접점을 관리하는 시스템입니다. 그룹웨어는 전자결재, 메일, 일정처럼 직원들의 협업을 위한 도구입니다. 실제로는 CRM의 수주가 ERP의 매출로, 그룹웨어의 결재가 ERP의 전표로 이어지는 식으로 서로 연결되어 있습니다.

### Q. 고객사 ERP와 우리 제품을 연동해야 합니다. 어떻게 접근하시겠습니까?

먼저 연동 목적과 읽기만 하는지 쓰기도 하는지를 확인합니다. 그다음 ERP가 제공하는 연동 방식을 조사합니다. 공식 API가 있으면 그것을 쓰고, 없으면 읽기 전용 DB 계정이나 인터페이스 테이블, 파일 연계를 검토합니다. 쓰기가 필요하면 처음에는 사람이 승인하는 단계를 두고, 실패했을 때 재처리와 되돌리는 방법을 함께 설계합니다.

### Q. 마스터 데이터와 트랜잭션 데이터의 차이는 무엇인가요?

마스터 데이터는 거래처, 품목, 직원처럼 잘 바뀌지 않는 기준 정보이고, 트랜잭션 데이터는 주문, 입출고, 전표처럼 업무가 일어날 때마다 쌓이는 기록입니다. 트랜잭션은 마스터를 참조하므로 마스터 데이터의 품질이 나쁘면 모든 분석이 흔들립니다.

### Q. CRM 데이터로 AI가 할 수 있는 일은 무엇인가요?

이탈 가능성이 높은 고객 예측, 성사 가능성에 따른 리드 점수, 상담 내용 요약과 분류, 다음 행동 추천, 고객별 맞춤 메시지 초안 작성 같은 일을 할 수 있습니다. 다만 결과가 영업이나 상담 담당자의 기존 업무 화면 안에서 보여야 실제로 쓰입니다.

### Q. 업무 시스템에 AI가 직접 데이터를 쓰게 해도 되나요?

처음부터는 권하지 않습니다. 먼저 읽기 전용으로 가치를 증명하고, 쓰기가 필요한 경우에도 AI가 초안을 만들고 사람이 승인하는 구조로 시작합니다. 쓰기 범위를 좁게 제한하고, 모든 변경을 기록하고, 되돌릴 수 있게 만든 뒤에 자동화 범위를 넓힙니다.
