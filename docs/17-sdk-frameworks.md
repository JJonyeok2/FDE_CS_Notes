# 17. SDK와 AI 프레임워크

> 한 줄 요약: 고객사 개발자에게 우리 제품을 쓰게 하는 통로가 SDK이고, FDE가 AI 기능을 빠르게 만드는 도구도 SDK와 프레임워크다. 무엇이 무엇을 감싸고 있는지, 언제 프레임워크를 쓰고 언제 직접 짜야 하는지 알아야 한다.

## 개념 요약

### 라이브러리, SDK, 프레임워크, API

| 용어 | 의미 | 예 |
| --- | --- | --- |
| API | 시스템이 외부에 열어 둔 약속된 호출 방법 | REST 엔드포인트 `POST /v1/messages` |
| 라이브러리 | 내가 필요할 때 불러 쓰는 코드 묶음 | `requests`, `pandas` |
| SDK | 특정 플랫폼을 쓰기 쉽게 만든 도구 모음. 클라이언트 라이브러리, 타입, 인증, 재시도, 예제, 문서를 포함 | AWS SDK(boto3), 각 LLM 제공사의 Python, TypeScript SDK |
| 프레임워크 | 정해진 구조 안에 내 코드를 끼워 넣음. 흐름의 주도권이 프레임워크에 있다 | Django, Next.js, LangGraph |

"라이브러리는 내가 부르고, 프레임워크는 나를 부른다."

### SDK가 해 주는 일

API를 직접 HTTP로 호출할 수도 있지만, SDK가 다음을 대신해 준다.

- **인증**: 키를 헤더에 넣고, 토큰을 갱신한다
- **타입**: 요청과 응답의 형식을 코드에서 바로 알 수 있다. 오타를 편집기가 잡아 준다
- **재시도와 타임아웃**: 일시적 오류와 429를 지수 백오프로 재시도한다
- **페이지네이션**: 여러 페이지 결과를 반복문 하나로 받는다
- **스트리밍**: 응답을 조각 단위로 받는 처리를 간단하게
- **오류 처리**: HTTP 상태 코드를 의미 있는 예외로 바꾼다

```python
# SDK 없이: 직접 HTTP
import requests
r = requests.post(URL, headers={"x-api-key": KEY, ...}, json={...}, timeout=30)
r.raise_for_status()
data = r.json()

# SDK로
client = Client()            # 키는 환경 변수에서 읽음
resp = client.messages.create(model=..., messages=[...])   # 재시도, 타입, 오류 처리 포함
```

### 좋은 SDK의 조건

FDE는 SDK를 **쓰는 사람**이기도 하고, 고객의 불편을 제품 팀에 전달해 SDK를 **고치게 하는 사람**이기도 하다.

- 5분 안에 첫 호출이 성공한다 (빠른 시작 문서)
- 언어의 관례를 따른다 (Python은 Python답게, TypeScript는 TypeScript답게)
- 오류 메시지가 무엇을 고쳐야 하는지 알려 준다
- 버전 관리가 명확하다. **시맨틱 버저닝**: `주.부.수` 중 주 버전이 오르면 호환이 깨지는 변경
- 하위 호환을 지키고, 기능을 없앨 때는 미리 예고(deprecation)한다
- 예제 코드가 실제로 돌아간다

### LLM 제공사 SDK

각 모델 제공사(Anthropic, OpenAI, Google 등)는 Python과 TypeScript를 중심으로 공식 SDK를 제공한다. 공통적으로 다루는 기능:

- 메시지 생성, 스트리밍
- 도구 사용(함수 호출): 도구 정의를 넘기고, 모델이 요청한 도구를 실행해 결과를 돌려주는 반복
- 구조화된 출력
- 이미지, 문서 입력
- 프롬프트 캐싱, 배치 처리
- 토큰 사용량 확인

제공사를 바꾸거나 여러 모델을 섞어 써야 하면 **모델 게이트웨이**(여러 제공사를 하나의 인터페이스로 감싸는 라이브러리나 프록시)를 검토한다. 다만 공통분모만 남아 각 제공사 고유 기능을 못 쓸 수 있다.

### 에이전트 SDK

모델 제공사들은 도구 사용 반복, 핸드오프, 가드레일, 트레이스 같은 에이전트의 공통 부품을 묶은 **에이전트용 SDK**도 내놓고 있다. 직접 반복문을 짜는 것보다 빠르게 시작할 수 있지만, 해당 제공사의 모델과 방식에 묶이는 정도를 확인한다. 이름과 기능이 빠르게 바뀌는 영역이라 쓰기 전에 공식 문서를 확인한다.

### AI 애플리케이션 프레임워크

| 프레임워크 | 성격 | 잘 맞는 경우 |
| --- | --- | --- |
| LangChain | LLM, 검색, 도구를 잇는 부품 모음. 연동 대상이 매우 많다 | 다양한 연동을 빠르게 붙여 보는 프로토타입 |
| LangGraph | 상태와 노드, 간선으로 흐름을 그래프로 정의. 분기, 반복, 사람 승인, 중단 후 재개 | 단계와 상태가 복잡한 워크플로와 에이전트 |
| LlamaIndex | 문서 수집, 색인, 검색에 강함 | RAG 중심 애플리케이션 |
| CrewAI, AutoGen 계열 | 역할을 가진 여러 에이전트의 협업을 추상화 | 멀티 에이전트 실험 |
| DSPy | 프롬프트를 손으로 쓰는 대신 프로그램처럼 정의하고 평가 데이터로 최적화 | 평가 세트가 있고 프롬프트를 체계적으로 개선하려 할 때 |

### 프레임워크를 쓸 것인가, 직접 짤 것인가

**쓰면 좋은 점**

- 빠르게 시작한다. 연동, 검색, 상태 관리가 이미 있다
- 팀원들이 같은 구조를 쓴다

**쓰면 생기는 문제**

- 추상화가 두꺼워서 **실제로 모델에 무엇이 전달되는지** 안 보인다. 디버깅이 어려워진다
- 버전 업데이트가 잦고 호환이 깨지기도 한다
- 프레임워크가 지원하지 않는 방식으로 바꾸려면 우회해야 한다
- 고객 환경에 의존성이 많이 늘어난다

**판단 기준**

- 모델 API 호출과 반복문 몇 개로 되는 일이면 **직접** 짠다. 생각보다 짧다
- 상태, 분기, 재시도, 중단 후 재개, 사람 승인처럼 직접 짜면 복잡한 흐름이 핵심이면 프레임워크(예: LangGraph)를 쓴다
- 프레임워크를 써도 **모델에 실제로 가는 프롬프트와 응답은 항상 볼 수 있게** 로그를 남긴다

### 관측과 평가 도구

| 분류 | 하는 일 |
| --- | --- |
| LLM 관측(트레이싱) | 각 호출의 입력, 출력, 토큰, 지연, 비용을 기록하고 단계별로 펼쳐 봄 |
| 평가 | 평가 세트를 돌려 점수를 기록하고 버전끼리 비교 |
| 프롬프트 관리 | 프롬프트를 코드 밖에서 버전 관리 |

LangSmith, Langfuse(직접 설치 가능), Arize Phoenix 같은 도구가 있다. 표준 형식(OpenTelemetry)으로 기록하면 도구를 바꾸기 쉽다. 고객 데이터가 외부 관측 서비스로 나가도 되는지 반드시 확인한다. 안 된다면 직접 설치할 수 있는 도구를 쓴다.

### 고객용 SDK를 만들거나 설명할 때

FDE는 고객사 개발자가 우리 제품을 붙이도록 돕는다.

- 고객이 쓰는 언어와 환경을 먼저 확인한다 (Java만 쓰는 회사에 Python SDK만 있으면 곤란하다)
- 빠른 시작 예제를 고객 데이터와 비슷한 상황으로 만들어 준다
- 고객이 막힌 지점을 기록해 제품 팀에 전달한다. 같은 질문이 세 번 나오면 문서나 SDK를 고쳐야 한다는 신호다

## 현장에서 만나는 상황

### 상황 1: SDK를 업데이트했더니 고객 연동이 깨졌다

- 변경 기록(changelog)에서 호환을 깨는 변경을 확인한다
- 고객 환경에서는 **버전을 고정**하고(`requirements.txt`, `package-lock.json`), 테스트 환경에서 새 버전을 확인한 뒤 올린다

### 상황 2: 프레임워크로 만든 에이전트의 동작을 설명할 수 없다

- 모델에 실제로 전달되는 프롬프트를 로그로 뽑는다. 프레임워크가 숨겨서 넣는 지시가 있을 수 있다
- 핵심 부분은 프레임워크 없이 직접 호출로 재현해 비교한다

### 상황 3: 고객이 Java나 C#만 쓴다

- 공식 SDK가 없는 언어라면 REST API를 직접 호출하는 예제를 만들어 준다
- 또는 우리 쪽에서 얇은 중간 서비스를 두고 고객은 익숙한 방식으로 그 서비스만 호출하게 한다

### 상황 4: 폐쇄망에서 SDK 설치가 안 된다

- 패키지와 의존성을 미리 받아 반입한다(`pip download`, 오프라인 설치)
- 외부 모델 API를 못 쓰는 환경이면 사내 모델 서버의 API 형식이 무엇인지 확인한다. 많은 모델 서빙 도구가 널리 쓰이는 API 형식을 흉내 내므로 기존 SDK의 접속 주소만 바꿔 쓸 수 있는 경우가 많다

## 면접 예상 질문

### Q. API와 SDK의 차이는 무엇인가요?

API는 시스템이 외부에 열어 둔 호출 규약이고, SDK는 그 API를 특정 언어에서 쉽게 쓰도록 감싼 도구 모음입니다. SDK는 인증, 타입, 재시도, 페이지네이션, 오류 처리를 대신해 주므로 개발자는 업무 로직에 집중할 수 있습니다.

### Q. 라이브러리와 프레임워크의 차이는 무엇인가요?

라이브러리는 내 코드가 필요할 때 호출하는 도구이고, 프레임워크는 정해진 구조 안에 내 코드를 끼워 넣으면 프레임워크가 흐름을 제어하며 내 코드를 호출합니다. 제어의 주도권이 누구에게 있느냐의 차이입니다.

### Q. LangChain 같은 프레임워크를 쓰는 것에 대해 어떻게 생각하나요?

빠르게 프로토타입을 만들고 다양한 연동을 붙이는 데는 유용합니다. 다만 추상화 때문에 모델에 실제로 무엇이 전달되는지 보기 어려워 디버깅이 힘들고, 버전 변경도 잦습니다. 단순한 호출은 직접 짜고, 상태와 분기가 복잡한 흐름처럼 프레임워크의 이점이 분명한 곳에 선택적으로 쓰며, 실제 프롬프트는 항상 로그로 확인합니다.

### Q. 좋은 SDK의 조건은 무엇인가요?

처음 쓰는 사람이 몇 분 안에 첫 호출에 성공할 수 있어야 하고, 해당 언어의 관례를 따르며, 오류 메시지가 해결 방법을 알려 줘야 합니다. 시맨틱 버저닝으로 호환이 깨지는 변경을 명확히 하고, 기능을 없앨 때는 미리 예고해야 합니다.

### Q. 시맨틱 버저닝을 설명해 주세요.

버전을 주, 부, 수 세 숫자로 나눠 주 버전은 호환이 깨지는 변경, 부 버전은 호환되는 기능 추가, 수 버전은 버그 수정에 올립니다. 사용자는 버전 번호만 보고 업데이트해도 안전한지 판단할 수 있습니다.
