# 6. 클라우드와 배포

> 한 줄 요약: 제품을 고객이 쓸 수 있게 올리는 방법은 하나가 아니다. 우리 클라우드, 고객의 클라우드, 고객의 사내 서버 각각의 차이와 제약을 알아야 한다.

## 개념 요약

### 배포 형태

| 형태 | 설명 | 특징 |
| --- | --- | --- |
| SaaS | 우리 클라우드에서 운영, 고객은 접속만 | 운영이 쉽다. 데이터가 고객 밖으로 나온다 |
| 고객 클라우드(VPC) 배포 | 고객의 클라우드 계정 안에 설치 | 데이터가 고객 통제 안에 있다. 우리 접근이 제한된다 |
| 온프레미스 | 고객의 사내 서버에 설치 | 보안 요구가 가장 강한 곳. 설치와 업데이트가 어렵다 |
| 폐쇄망 | 인터넷이 차단된 환경 | 모든 것을 반입해야 한다. 외부 LLM API를 못 쓴다 |

금융, 공공, 의료, 제조 대기업은 아래쪽으로 갈수록 많다. FDE가 필요한 이유이기도 하다.

### 클라우드 기본 구성 요소 (AWS 기준)

| 분류 | 서비스 | 역할 |
| --- | --- | --- |
| 컴퓨팅 | EC2 | 가상 서버 |
| | Lambda | 서버 관리 없이 함수 실행 |
| | ECS, EKS | 컨테이너 실행 |
| 저장 | S3 | 파일(객체) 저장 |
| | RDS | 관리형 관계형 DB |
| | DynamoDB | 관리형 NoSQL |
| 네트워크 | VPC | 격리된 가상 네트워크 |
| | ALB | 로드 밸런서 |
| | API Gateway | API 관문 |
| | CloudFront | CDN |
| 권한 | IAM | 누가 무엇을 할 수 있는지 |
| 관측 | CloudWatch | 로그와 지표 |
| 비동기 | SQS, SNS | 큐, 알림 |

다른 클라우드도 이름만 다르고 개념은 같다. (GCP의 Cloud Run, Azure의 Blob Storage 등)

### VPC와 네트워크

- **VPC**: 클라우드 안의 내 전용 네트워크
- **퍼블릭 서브넷**: 인터넷과 직접 통신 가능. 로드 밸런서를 둔다.
- **프라이빗 서브넷**: 외부에서 직접 접근 불가. 애플리케이션 서버와 DB를 둔다.
- **보안 그룹**: 인스턴스 단위 방화벽. 허용 규칙만 있다.
- **NAT 게이트웨이**: 프라이빗 서브넷의 서버가 밖으로 나갈 때 쓴다.

연결이 타임아웃되면 보안 그룹부터 본다. 클라우드 네트워크 문제의 대부분이 여기에 있다.

### IAM

- **최소 권한 원칙**: 필요한 권한만 준다.
- 사람에게는 **사용자**, 서비스에는 **역할**을 부여한다. 서버에 액세스 키를 파일로 넣지 않고 역할을 붙인다.
- 액세스 키를 코드 저장소에 올리는 것은 가장 흔하고 가장 비싼 사고다.

### 서버리스

- 서버를 직접 관리하지 않고, 요청이 올 때만 실행되고 쓴 만큼만 낸다.
- **장점**: 운영 부담이 적고, 트래픽이 없으면 비용이 거의 없고, 자동으로 늘어난다.
- **단점**: 한동안 호출이 없다가 처음 실행될 때 느리다(**콜드 스타트**), 실행 시간에 제한이 있다, 상태를 유지할 수 없다, 로컬에서 재현하기 어렵다.
- LLM 호출처럼 오래 걸리는 작업은 실행 시간 제한과 API Gateway의 타임아웃에 걸릴 수 있다. 비동기 처리나 스트리밍을 검토한다.

### 환경 분리와 설정

- **개발, 스테이징, 운영** 환경을 나눈다.
- 코드는 같고 **설정만 다르게** 한다. 설정은 환경 변수로 주입한다.
- 비밀 값(API 키, DB 비밀번호)은 비밀 저장소(Secrets Manager 등)에 둔다.

### CI/CD

- **CI**: 코드를 올릴 때마다 자동으로 빌드하고 테스트한다.
- **CD**: 통과한 것을 자동으로 배포한다.
- GitHub Actions가 대표적이다. 이 사이트도 푸시하면 자동 배포된다.

### 배포 전략

| 전략 | 방식 | 특징 |
| --- | --- | --- |
| 롤링 | 서버를 하나씩 교체 | 추가 자원이 적게 든다 |
| 블루-그린 | 새 환경을 통째로 띄우고 트래픽 전환 | 되돌리기가 즉시 가능. 자원이 두 배 |
| 카나리 | 일부 사용자에게만 먼저 | 문제를 작게 발견한다 |

어떤 전략이든 **되돌리는 방법**이 준비되어 있어야 한다. DB 스키마 변경은 되돌리기 어려우므로 이전 버전 코드와도 호환되게 단계적으로 바꾼다.

### IaC

인프라를 코드로 정의한다(Terraform, CloudFormation, CDK). 같은 환경을 반복해서 만들 수 있어, 고객마다 환경을 새로 구성해야 하는 FDE에게 특히 유용하다.

## 현장에서 만나는 상황

### 상황 1: 고객이 "우리 데이터는 밖으로 못 나갑니다"라고 한다

- 무엇이 못 나가는지 구체적으로 묻는다. 원본 전체인가, 개인정보만인가, 국외 이전이 문제인가.
- 선택지: 고객 VPC 안에 배포, 개인정보를 가린 뒤 처리, 국내 리전 사용, 사내에서 돌릴 수 있는 모델 사용.
- LLM을 쓰는 제품이라면 **외부 모델 API로 데이터가 전송되는 것**이 쟁점이 된다. 제공사의 데이터 보관과 학습 사용 정책을 정확히 알고 설명할 수 있어야 한다.

### 상황 2: 고객 클라우드 계정에 배포해야 한다

- 필요한 권한 목록을 미리 정리해 전달한다. 권한 승인에 가장 시간이 걸린다.
- 설치를 IaC와 스크립트로 만들어 사람 손을 줄인다.
- 우리가 접근할 수 없을 때를 대비해 로그 수집과 진단 방법을 합의한다.

### 상황 3: 배포했더니 장애가 났다

1. 먼저 되돌린다. 원인 분석은 그다음이다.
2. 무엇이 바뀌었는지 확인한다: 코드, 설정, 환경 변수, DB 스키마, 의존성 버전.
3. 스테이징에서 왜 못 잡았는지 확인한다. 대개 운영과 스테이징의 설정이나 데이터가 달라서다.

### 상황 4: "비용이 너무 많이 나와요"

- 비용 내역을 서비스별로 본다. 흔한 범인: 켜 둔 채 잊은 자원, NAT 게이트웨이의 데이터 전송, 과도한 로그 저장, LLM 토큰 사용량.

## 면접 예상 질문

### Q. 서버리스의 장단점은 무엇인가요?

서버를 관리하지 않아도 되고 사용한 만큼만 비용을 내며 자동으로 확장된다는 장점이 있습니다. 반면 콜드 스타트로 첫 응답이 느릴 수 있고, 실행 시간 제한이 있으며, 상태를 유지하지 못합니다. 트래픽이 불규칙하고 요청이 짧은 서비스에 잘 맞습니다.

### Q. 온프레미스 배포는 SaaS와 무엇이 다른가요?

고객의 환경에 우리가 맞춰야 한다는 점이 다릅니다. 운영체제와 네트워크 정책이 제각각이고, 우리가 직접 접속해 문제를 볼 수 없는 경우가 많으며, 업데이트도 고객 일정에 따라야 합니다. 그래서 설치를 자동화하고, 환경 차이를 컨테이너로 줄이고, 고객이 직접 수집해 줄 수 있는 진단 수단을 준비해야 합니다.

### Q. 비밀 값은 어떻게 관리하나요?

코드나 저장소에 넣지 않고 비밀 저장소나 환경 변수로 주입합니다. 환경별로 값을 분리하고, 접근 권한을 최소화하며, 유출이 의심되면 즉시 교체할 수 있게 합니다.

### Q. 무중단 배포는 어떻게 하나요?

로드 밸런서 뒤에 서버를 여러 대 두고, 롤링이나 블루-그린 방식으로 새 버전을 띄워 상태 확인을 통과한 뒤 트래픽을 넘깁니다. DB 스키마 변경은 이전 버전 코드와 호환되도록 단계를 나눠 적용합니다.

### Q. 퍼블릭 서브넷과 프라이빗 서브넷은 왜 나누나요?

외부에 노출할 필요가 없는 자원을 인터넷에서 직접 접근할 수 없게 하기 위해서입니다. 로드 밸런서만 퍼블릭에 두고 애플리케이션 서버와 DB는 프라이빗에 두면 공격 표면이 줄어듭니다.
