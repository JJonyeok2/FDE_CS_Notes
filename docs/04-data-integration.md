# 4. 데이터 통합

> 한 줄 요약: 고객의 데이터는 여러 시스템에 서로 다른 모양으로 흩어져 있다. 이것을 옮기고, 맞추고, 믿을 수 있게 만드는 일이 FDE 업무의 큰 부분이다.

## 개념 요약

### ETL과 ELT

- **ETL**: 꺼내고(Extract) 변환한 뒤(Transform) 적재한다(Load). 변환을 중간 서버에서 한다.
- **ELT**: 꺼내서 원본 그대로 적재한 뒤 저장소 안에서 변환한다. 데이터 웨어하우스의 연산 능력이 좋아지면서 일반화되었다. 원본이 남아 있어 변환 로직을 고쳐 다시 돌리기 쉽다.

### 배치와 스트리밍

| | 배치 | 스트리밍 |
| --- | --- | --- |
| 방식 | 모아서 한 번에 | 생기는 즉시 |
| 지연 | 분~하루 | 초 이하 |
| 복잡도 | 낮음 | 높음 |
| 예 | 매일 새벽 매출 집계 | 이상 거래 탐지 |

"실시간이 필요하다"는 요구를 받으면 **얼마나 늦어도 괜찮은지**를 먼저 묻는다. 대부분은 5분 주기 배치로 충분하다.

### 전체 적재와 증분 적재

- **전체 적재**: 매번 전부 다시 가져온다. 단순하고 틀릴 일이 적지만 데이터가 크면 불가능하다.
- **증분 적재**: 바뀐 것만 가져온다. `updated_at` 컬럼 기준으로 가져오거나, **CDC**(Change Data Capture)로 DB의 변경 로그를 읽는다.
- `updated_at` 방식은 **삭제된 행을 잡지 못한다**는 한계가 있다.

### 멱등성

같은 작업을 여러 번 돌려도 결과가 같아야 한다. 파이프라인은 반드시 실패하고 재실행되기 때문이다.

- INSERT만 하면 재실행 시 중복이 생긴다. **UPSERT**(있으면 갱신, 없으면 삽입)를 쓰거나, 해당 구간을 지우고 다시 넣는다.
- 고유 키를 정하는 것이 출발점이다.

### 전달 보장

- **최대 한 번(at-most-once)**: 유실될 수 있다.
- **최소 한 번(at-least-once)**: 중복될 수 있다. 가장 흔하다.
- **정확히 한 번(exactly-once)**: 어렵다. 보통 "최소 한 번 + 멱등한 처리"로 같은 효과를 낸다.

### 스키마와 데이터 형식

- **형식**: CSV(단순하지만 타입이 없고 깨지기 쉬움), JSON(유연함), Parquet(열 지향, 압축, 분석에 적합)
- **스키마 진화**: 원본 시스템의 컬럼이 예고 없이 추가되거나 바뀐다. 파이프라인이 조용히 틀린 데이터를 넣는 것이 가장 위험하다. 스키마가 바뀌면 실패하고 알림을 보내게 한다.

### 데이터 품질

들어오는 데이터를 믿지 않는다. 최소한 다음을 검사한다.

- **완전성**: 필수 값이 비어 있지 않은가, 행 수가 평소와 비슷한가
- **유일성**: 키가 중복되지 않는가
- **유효성**: 범위와 형식이 맞는가 (음수 금액, 미래 날짜)
- **정합성**: 참조하는 대상이 존재하는가
- **최신성**: 데이터가 제때 들어왔는가

### 엔티티 매칭

시스템 A의 "삼성전자(주)"와 시스템 B의 "Samsung Electronics"가 같은 대상임을 알아내는 문제다. 공통 키(사업자등록번호 등)가 있으면 그것을 쓰고, 없으면 정규화(공백, 괄호, 대소문자 제거) 후 유사도 매칭을 하고 애매한 건은 사람이 확인하게 한다.

### 흔한 함정

- **인코딩**: 한국 기업의 오래된 파일은 EUC-KR(CP949)인 경우가 많다. UTF-8로 읽으면 깨진다.
- **시간대**: 저장은 UTC로, 표시는 현지 시간으로 한다. 시간대 정보 없는 시각 값은 반드시 기준을 확인한다.
- **엑셀**: 앞자리 0이 사라진다(전화번호, 우편번호), 긴 숫자가 지수 표기로 바뀐다, 날짜가 숫자로 바뀐다, 병합 셀과 여러 줄 머리글이 있다.
- **구분자**: 값 안에 쉼표나 줄바꿈이 들어 있다.

## 현장에서 만나는 상황

### 상황 1: 고객이 엑셀 파일 묶음을 준다

1. 파일마다 구조가 같은지 먼저 확인한다. 연도별로 컬럼이 다른 경우가 흔하다.
2. 인코딩, 머리글 위치, 병합 셀, 숨겨진 시트를 본다.
3. 변환 규칙을 **코드로** 남긴다. 손으로 고치면 다음 달에 또 손으로 고쳐야 한다.
4. 변환 결과의 행 수와 합계를 원본과 대조한다.
5. 이상한 값의 목록을 만들어 고객에게 확인받는다. 임의로 고치지 않는다.

### 상황 2: "대시보드 숫자가 우리 보고서랑 달라요"

- **확인 순서**: 집계 기준 시점(어제 자정인가 오늘 아침인가), 포함 범위(취소 건, 테스트 계정), 시간대, 중복 적재, 적재 누락 순으로 본다.
- 한 건을 골라 원본부터 끝까지 따라간다. 전체를 보지 말고 **차이 나는 한 건**을 찾는다.
- **고객에게 설명하는 말**: "두 숫자는 계산 기준이 다릅니다. 보고서는 결제일 기준, 대시보드는 주문일 기준입니다. 어느 쪽에 맞출지 정해 주시면 됩니다."

### 상황 3: 야간 배치가 실패했다

- 어디까지 처리되었는가, 다시 돌려도 안전한가(멱등한가)를 확인한다.
- 원인을 고친 뒤 실패한 구간만 재실행(백필)한다.
- 실패를 사람이 아침에 발견하는 구조라면 알림을 추가한다.

### 상황 4: 원본 시스템 담당자가 컬럼을 바꿨다

- 조용히 깨지는 것을 막기 위해 스키마 검사를 파이프라인 맨 앞에 둔다.
- 원본 담당자와 변경 사전 공유 약속(데이터 계약)을 만든다.

## 면접 예상 질문

### Q. ETL과 ELT의 차이는 무엇인가요?

변환을 적재 전에 하느냐 후에 하느냐의 차이입니다. ELT는 원본을 그대로 저장소에 넣고 그 안에서 변환하므로, 원본이 보존되어 변환 로직이 바뀌어도 다시 계산할 수 있습니다.

### Q. 파이프라인이 중간에 실패하면 어떻게 하나요?

재실행해도 결과가 같도록 처음부터 멱등하게 설계합니다. 고유 키 기준으로 UPSERT를 하거나 처리 구간을 지우고 다시 넣는 방식을 씁니다. 그러면 실패한 지점부터 안전하게 다시 돌릴 수 있습니다.

### Q. 데이터 품질은 어떻게 확인하나요?

행 수, 필수 값의 NULL 비율, 키 중복, 값의 범위, 원본과의 합계 대조를 자동 검사로 넣습니다. 검사에 실패하면 잘못된 데이터가 뒤로 흘러가지 않게 파이프라인을 멈추고 알림을 보냅니다.

### Q. 서로 다른 시스템의 고객 데이터를 합쳐야 합니다. 어떻게 하시겠습니까?

먼저 공통으로 쓸 수 있는 식별자가 있는지 찾습니다. 없다면 이름과 연락처를 정규화한 뒤 일치 규칙을 단계별로 적용하고, 확실한 것은 자동으로 합치되 애매한 것은 사람이 검토하게 합니다. 합친 근거를 기록해 나중에 되돌릴 수 있게 합니다.

### Q. 실시간 처리가 필요하다는 요구를 받으면 어떻게 하나요?

실제로 허용되는 지연이 얼마인지 먼저 확인합니다. 초 단위가 꼭 필요한 경우는 드물고, 짧은 주기의 배치로 충분한 경우가 많습니다. 스트리밍은 운영 복잡도가 크게 늘어나므로 필요가 확인될 때 선택합니다.
