# 2. API와 인증

> 한 줄 요약: FDE의 일은 대부분 "우리 제품과 고객의 시스템을 붙이는 것"이다. 붙이는 방법(API)과 안전하게 붙이는 방법(인증)을 알아야 한다.

## 개념 요약

### API 스타일

| 스타일 | 특징 | 주로 쓰는 곳 |
| --- | --- | --- |
| REST | 자원을 URL로, 행위를 HTTP 메서드로 표현 | 대부분의 웹 서비스 |
| GraphQL | 클라이언트가 필요한 필드만 골라 요청 | 화면이 복잡한 프론트엔드 |
| gRPC | 바이너리(Protocol Buffers), 빠름, 스키마 엄격 | 서버 간 내부 통신 |
| SOAP | XML 기반, 오래된 표준 | 금융, 공공, 오래된 기업 시스템 |
| 웹훅 | 일이 생기면 상대가 우리에게 호출 | 결제 완료, 상태 변경 알림 |

고객사에서는 SOAP이나 파일 전송(SFTP)처럼 오래된 방식을 만나는 일이 많다. 최신 방식만 알면 곤란하다.

### 좋은 REST API의 조건

- 자원은 명사, 복수형으로 쓴다: `/orders/123`
- 상태 코드를 의미에 맞게 쓴다. 실패했는데 200을 주지 않는다.
- 목록은 **페이지네이션**을 제공한다. 오프셋 방식(`page=3`)은 단순하지만 뒤로 갈수록 느리고, 커서 방식(`after=abc`)은 빠르고 데이터가 바뀌어도 안정적이다.
- 버전을 둔다: `/v1/...`
- 오류 응답 형식을 통일한다.

### 폴링과 웹훅

- **폴링**: 우리가 주기적으로 물어본다. 구현이 쉽지만 낭비가 많고 지연이 생긴다.
- **웹훅**: 일이 생기면 상대가 알려 준다. 효율적이지만 우리가 요청을 받을 주소가 외부에 열려 있어야 하고, 서명 검증과 중복 처리가 필요하다.
- 고객사 방화벽이 인바운드를 막으면 웹훅을 쓸 수 없어 폴링으로 돌아가야 한다.

### 재시도, 멱등성, 레이트 리밋

- 네트워크는 실패한다. 재시도는 필수이고, 간격을 점점 늘리는 **지수 백오프**에 무작위 값(지터)을 더한다.
- 재시도하면 같은 요청이 두 번 처리될 수 있다. **멱등성 키**를 요청에 넣어 서버가 중복을 걸러 내게 한다. 결제에서 특히 중요하다.
- **레이트 리밋**에 걸리면 429를 받는다. `Retry-After` 헤더를 존중한다.

### 인증과 인가

- **인증(Authentication)**: 누구인가
- **인가(Authorization)**: 무엇을 할 수 있는가

### 인증 방식

| 방식 | 설명 | 주의점 |
| --- | --- | --- |
| API 키 | 긴 문자열을 헤더에 넣음 | 유출되면 끝. 코드에 넣지 말고 환경 변수나 비밀 저장소에 |
| 세션 쿠키 | 서버가 상태를 기억하고 쿠키로 식별 | 서버 여러 대면 세션 저장소 공유 필요 |
| JWT | 서명된 토큰에 정보를 담음. 서버가 상태를 안 가져도 됨 | 만료 전 무효화가 어렵다. 페이로드는 암호화가 아니라 인코딩일 뿐이다 |
| OAuth 2.0 | 비밀번호를 주지 않고 권한을 위임 | 흐름이 여러 가지라 상황에 맞게 골라야 함 |
| mTLS | 클라이언트도 인증서를 제시 | 인증서 발급과 갱신 관리가 필요 |

### OAuth 2.0

"이 앱이 내 구글 캘린더를 읽어도 좋다"를 비밀번호 공유 없이 허락하는 방법이다.

- **인가 코드 흐름**: 사용자가 로그인 화면에서 동의하면 앱이 코드를 받고, 그 코드를 토큰으로 교환한다. 사용자가 있는 웹과 모바일 앱에서 쓴다. (PKCE를 함께 쓴다)
- **클라이언트 자격 증명 흐름**: 사용자 없이 서버끼리 통신할 때 쓴다.
- **액세스 토큰**은 수명이 짧고, **리프레시 토큰**으로 새로 발급받는다.
- **스코프**로 권한 범위를 제한한다. 필요한 최소한만 요청한다.

### SSO: SAML과 OIDC

기업 고객은 거의 항상 "우리 회사 계정으로 로그인하게 해 달라"고 요구한다.

- **SSO**: 한 번 로그인하면 여러 서비스를 쓸 수 있다. 고객사의 **IdP**(Okta, Microsoft Entra ID 등)가 인증을 담당한다.
- **SAML**: XML 기반의 오래된 표준. 대기업에서 여전히 많이 쓴다.
- **OIDC**: OAuth 2.0 위에 신원 확인을 얹은 것. JSON과 JWT 기반이라 다루기 쉽다.
- **SCIM**: 사용자 계정의 생성과 삭제를 자동으로 동기화하는 표준. 퇴사자의 계정이 자동으로 막혀야 한다는 요구에 대응한다.

## 현장에서 만나는 상황

### 상황 1: "어제까지 되던 연동이 갑자기 401이에요"

- **확인 순서**
  1. 토큰이나 키가 만료되었는가
  2. 누군가 키를 재발급했는가
  3. 서버 시계가 어긋났는가 (JWT의 만료 시각 검증이 실패한다)
  4. 리프레시 토큰 갱신 로직이 실패하고 있었는가
- **고객에게 설명하는 말**: "연동에 쓰는 출입증의 유효 기간이 끝났습니다. 재발급하고, 앞으로는 자동으로 갱신되게 바꾸겠습니다."

### 상황 2: 고객사 시스템에 API가 없다

- 선택지를 순서대로 검토한다: 데이터베이스 직접 조회(읽기 전용 계정) → 파일 내보내기(CSV를 SFTP로) → 화면 자동화(RPA, 마지막 수단).
- 각 방법의 위험을 고객에게 설명한다. 화면 자동화는 화면이 바뀌면 깨진다.

### 상황 3: 데이터가 중복으로 들어갔다

- 재시도 때문에 같은 요청이 두 번 처리되었는지 본다.
- 웹훅은 **한 번 이상** 전달될 수 있다고 가정하고, 이벤트 ID로 중복을 걸러 낸다.

### 상황 4: 고객사 API가 느리고 호출 한도가 낮다

- 캐시, 변경분만 가져오기(증분 동기화), 호출을 큐에 넣어 속도 조절, 야간 배치를 검토한다.

## 면접 예상 질문

### Q. 인증과 인가의 차이는 무엇인가요?

인증은 요청한 사람이 누구인지 확인하는 것이고, 인가는 그 사람이 해당 작업을 할 권한이 있는지 확인하는 것입니다. HTTP 상태 코드로는 인증 실패가 401, 인가 실패가 403입니다.

### Q. JWT의 장단점은 무엇인가요?

서버가 세션 상태를 저장하지 않아도 토큰의 서명만 검증하면 되므로 서버를 늘리기 쉽습니다. 반면 한 번 발급하면 만료 전에 무효화하기 어렵고, 페이로드는 누구나 읽을 수 있으므로 민감한 정보를 넣으면 안 됩니다. 그래서 액세스 토큰의 수명을 짧게 하고 리프레시 토큰을 함께 씁니다.

### Q. OAuth 2.0을 설명해 주세요.

사용자가 비밀번호를 제3자 앱에 알려 주지 않고도, 자신의 자원에 대한 제한된 접근 권한을 위임하는 표준입니다. 사용자가 인가 서버에서 동의하면 앱은 인가 코드를 받고, 이를 액세스 토큰으로 교환해 API를 호출합니다. 스코프로 권한 범위를 제한합니다.

### Q. 외부 API 호출이 실패하면 어떻게 처리하나요?

먼저 실패의 종류를 구분합니다. 4xx는 요청이 잘못된 것이므로 재시도해도 소용없고, 5xx나 타임아웃은 일시적일 수 있으므로 지수 백오프로 재시도합니다. 재시도로 인한 중복 처리를 막기 위해 멱등성 키를 쓰고, 계속 실패하면 서킷 브레이커로 호출을 멈추고 알림을 보냅니다.

### Q. 웹훅을 받을 때 주의할 점은 무엇인가요?

요청이 진짜 상대에게서 온 것인지 서명을 검증해야 하고, 같은 이벤트가 여러 번 올 수 있으므로 이벤트 ID로 중복을 걸러야 합니다. 또 빠르게 200을 응답하고 실제 처리는 큐에 넣어 비동기로 해야 상대의 타임아웃으로 인한 재전송을 피할 수 있습니다.
