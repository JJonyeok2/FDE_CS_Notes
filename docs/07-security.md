# 7. 보안과 권한

> 한 줄 요약: 기업 고객에게 제품을 넣으려면 보안팀을 통과해야 한다. FDE는 보안 질문에 정확히 답하고, 고객 데이터를 다루는 사람으로서 스스로 사고를 내지 않아야 한다.

## 개념 요약

### 보안의 세 가지 목표

- **기밀성**: 허락된 사람만 볼 수 있다.
- **무결성**: 허락 없이 바뀌지 않는다.
- **가용성**: 필요할 때 쓸 수 있다.

### 암호화

- **대칭키**: 같은 키로 잠그고 푼다. 빠르다. (AES)
- **비대칭키**: 공개키로 잠그고 개인키로 푼다. 느리지만 키를 안전하게 나눌 수 있다. (RSA)
- **전송 중 암호화**: TLS
- **저장 시 암호화**: 디스크와 DB 암호화
- **해시**: 되돌릴 수 없는 단방향 변환. 비밀번호는 암호화가 아니라 **솔트를 넣은 느린 해시**(bcrypt, Argon2)로 저장한다.
- **인코딩은 암호화가 아니다.** Base64는 누구나 되돌릴 수 있다.

### 접근 제어

- **RBAC**: 역할에 권한을 주고 사용자에게 역할을 준다. (관리자, 편집자, 조회자)
- **ABAC**: 속성 조합으로 판단한다. (부서가 영업이고 지역이 서울인 데이터만)
- **행 수준 보안**: 같은 테이블이라도 사용자마다 볼 수 있는 행이 다르다.
- **최소 권한 원칙**: 필요한 만큼만, 필요한 동안만.

### 멀티 테넌시

여러 고객이 같은 시스템을 쓸 때 **고객 A가 고객 B의 데이터를 절대 볼 수 없어야** 한다.

- 격리 방식: DB 분리, 스키마 분리, 같은 테이블에 테넌트 ID 컬럼.
- 테넌트 ID 방식은 쿼리에서 조건 하나를 빠뜨리면 사고가 난다. 애플리케이션 코드가 아니라 DB나 프레임워크 수준에서 강제하는 편이 안전하다.

### 흔한 웹 취약점

| 취약점 | 내용 | 방어 |
| --- | --- | --- |
| SQL 인젝션 | 입력값이 쿼리의 일부로 실행됨 | 파라미터 바인딩 사용. 문자열 이어 붙이기 금지 |
| XSS | 악성 스크립트가 다른 사용자의 브라우저에서 실행됨 | 출력 시 이스케이프, CSP |
| CSRF | 로그인된 사용자의 권한으로 원치 않는 요청을 보내게 함 | CSRF 토큰, SameSite 쿠키 |
| 접근 제어 누락 | URL의 ID만 바꿔 남의 데이터 조회 | 서버에서 매번 소유권 확인 |
| 비밀 값 노출 | 키가 코드나 로그에 남음 | 비밀 저장소, 로그 마스킹 |
| SSRF | 서버가 공격자가 지정한 내부 주소로 요청하게 함 | 요청 대상 허용 목록 |

### LLM 고유의 위험

- **프롬프트 인젝션**: 문서나 웹 페이지 안에 숨겨진 지시문을 모델이 따르게 만든다. 모델이 읽는 외부 내용은 명령이 아니라 **데이터**로 취급하고, 모델이 쓸 수 있는 도구의 권한을 최소로 한다.
- **데이터 유출**: 검색 증강 생성에서 권한 없는 문서가 검색되어 답변에 섞인다. 검색 단계에서 사용자 권한으로 걸러야 한다.
- **과도한 권한**: 에이전트가 삭제나 전송 같은 되돌릴 수 없는 행동을 사람 확인 없이 한다.
- **민감 정보 입력**: 사용자가 개인정보를 프롬프트에 넣는다. 외부 모델로 보내기 전에 가린다.

### 개인정보

- **개인정보**: 개인을 알아볼 수 있는 정보. 이름, 연락처, 주민등록번호 등. 여러 정보를 결합해 알아볼 수 있어도 해당한다.
- **가명 처리**: 추가 정보 없이는 알아볼 수 없게 바꾼다.
- **익명 처리**: 어떤 방법으로도 알아볼 수 없게 한다.
- 원칙: 필요한 최소한만 수집하고, 목적 외로 쓰지 않고, 필요 없어지면 지운다.
- 한국에서는 개인정보 보호법이 기준이고, 유럽 고객은 GDPR이 적용된다.

### 감사 로그

누가, 언제, 무엇을 했는지 기록한다. 기업 고객의 필수 요구 사항이다. 로그 자체에 비밀번호나 개인정보가 남지 않게 한다.

### 인증과 규격

보안 설문지에서 자주 만나는 이름들이다. 무엇을 증명하는지 정도는 안다.

- **ISO 27001**: 정보보호 관리 체계 국제 표준
- **SOC 2**: 서비스 조직의 보안 통제에 대한 감사 보고서
- **ISMS-P**: 한국의 정보보호 및 개인정보보호 관리 체계 인증
- **CSAP**: 한국 공공기관에 클라우드 서비스를 제공하기 위한 보안 인증

## 현장에서 만나는 상황

### 상황 1: 고객 보안팀이 질문지를 보냈다

- 모르는 것을 추측으로 답하지 않는다. "확인 후 답변드리겠습니다"가 정답이다. 틀린 보안 답변은 계약 문제가 된다.
- 자주 나오는 질문에 대한 정확한 답을 미리 정리해 둔다.
  - 데이터는 어디에 저장되는가 (국가, 리전)
  - 전송과 저장 시 암호화하는가
  - 누가 고객 데이터에 접근할 수 있는가
  - 데이터는 언제 어떻게 삭제되는가
  - 고객 데이터가 AI 모델 학습에 쓰이는가
  - 장애나 침해가 발생하면 어떻게 알리는가

### 상황 2: 고객이 운영 DB 관리자 계정을 통째로 줬다

- 받지 않는다. 필요한 테이블에 대한 **읽기 전용 계정**을 다시 요청한다.
- 과도한 권한은 사고가 났을 때 나를 지켜 주지 못한다.

### 상황 3: 고객 데이터를 내 노트북에 받아야 할 것 같다

- 먼저 받아도 되는지 확인한다. 계약과 고객 정책에 따른다.
- 가능하면 고객 환경 안에서 작업한다. 받아야 한다면 필요한 최소한만, 개인정보는 가린 상태로, 작업 후 삭제한다.
- 고객 데이터를 개인용 AI 도구에 붙여 넣지 않는다.

### 상황 4: API 키를 저장소에 올려 버렸다

1. 즉시 키를 **폐기하고 재발급**한다. 커밋을 지우는 것으로는 부족하다. 이미 복제되었을 수 있다.
2. 해당 키의 사용 기록을 확인한다.
3. 숨기지 않고 보고한다.
4. 재발 방지: 커밋 전 비밀 값 검사 도구, `.gitignore`, 비밀 저장소.

### 상황 5: "이 사용자는 이 문서를 보면 안 되는데 AI가 답해 줬어요"

- 검색 단계에서 권한 필터가 적용되는지 확인한다. 생성 단계에서 막으려 하면 늦다.
- 색인할 때 문서의 접근 권한 정보를 함께 저장하고, 검색 시 질문한 사용자의 권한으로 거른다.

## 면접 예상 질문

### Q. 비밀번호는 어떻게 저장해야 하나요?

평문이나 복호화 가능한 암호화가 아니라, 사용자마다 다른 솔트를 넣은 단방향 해시로 저장합니다. 해시 함수는 무차별 대입을 어렵게 하도록 일부러 느리게 설계된 bcrypt나 Argon2를 씁니다.

### Q. SQL 인젝션은 무엇이고 어떻게 막나요?

사용자 입력이 쿼리 문자열에 그대로 이어 붙여져 의도하지 않은 SQL이 실행되는 공격입니다. 입력을 쿼리 구조와 분리하는 파라미터 바인딩을 쓰면 막을 수 있습니다. ORM을 쓰더라도 직접 쿼리를 작성하는 부분은 따로 확인합니다.

### Q. 고객 데이터를 다룰 때 무엇을 주의하나요?

필요한 최소한의 데이터와 권한만 요청하고, 가능한 한 고객 환경 안에서 작업합니다. 개인정보는 가린 뒤 다루고, 로그나 외부 도구로 새어 나가지 않게 합니다. 작업이 끝나면 접근 권한을 반납하고 받은 데이터는 삭제합니다.

### Q. 프롬프트 인젝션은 무엇이고 어떻게 대응하나요?

모델이 처리하는 문서나 사용자 입력 안에 숨겨진 지시문이 원래 지시를 덮어쓰게 만드는 공격입니다. 완벽한 방어는 어렵기 때문에 여러 겹으로 대응합니다. 외부 내용을 지시가 아닌 데이터로 구분하고, 모델이 쓸 수 있는 도구와 권한을 최소화하고, 되돌릴 수 없는 행동에는 사람의 확인을 넣습니다.

### Q. RBAC이 무엇인가요?

권한을 사용자에게 직접 주지 않고 역할에 부여한 뒤 사용자에게 역할을 할당하는 접근 제어 방식입니다. 사람이 바뀌어도 역할만 바꿔 주면 되므로 관리가 쉽습니다.
