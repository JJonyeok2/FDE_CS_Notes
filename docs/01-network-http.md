# 1. 네트워크와 HTTP

> 한 줄 요약: 고객사 환경에서 가장 먼저, 가장 자주 만나는 문제는 "연결이 안 된다"이다. 요청 한 건이 지나가는 경로를 계층별로 나눠 볼 수 있어야 한다.

## 개념 요약

### 요청 한 건의 여정

브라우저에 주소를 입력하면 다음 순서로 일이 일어난다.

1. **DNS 조회**: 도메인 이름을 IP 주소로 바꾼다.
2. **TCP 연결**: 3-way handshake(SYN, SYN-ACK, ACK)로 연결을 맺는다.
3. **TLS 핸드셰이크**: HTTPS라면 인증서를 검증하고 암호화 키를 합의한다.
4. **HTTP 요청과 응답**: 메서드, 경로, 헤더, 본문을 보내고 상태 코드와 응답을 받는다.
5. **렌더링**: 브라우저가 받은 내용을 화면에 그린다.

문제가 생기면 **몇 번째 단계에서 멈췄는지**를 먼저 찾는다.

### TCP와 UDP

| | TCP | UDP |
| --- | --- | --- |
| 연결 | 연결을 맺고 시작 | 연결 없이 보냄 |
| 신뢰성 | 순서 보장, 재전송 | 보장 없음 |
| 용도 | HTTP, DB 연결 | DNS 조회, 영상 스트리밍, HTTP/3(QUIC) |

### IP, 포트, 사설망

- **IP 주소**는 기기를, **포트**는 그 기기 안의 프로그램을 가리킨다. (HTTP 80, HTTPS 443, SSH 22, PostgreSQL 5432, MySQL 3306)
- **사설 IP**(10.x, 172.16~31.x, 192.168.x)는 내부망에서만 통하고, 외부로 나갈 때 **NAT**가 공인 IP로 바꿔 준다.
- 고객사 서버가 사설망에만 있다면 외부에서 직접 접근할 수 없다. VPN, 배스천 호스트, 전용선 같은 경로가 필요하다.

### HTTP 기본

- **메서드**: GET(조회), POST(생성), PUT(전체 수정), PATCH(부분 수정), DELETE(삭제)
- **멱등성**: 같은 요청을 여러 번 보내도 결과가 같은 성질. GET, PUT, DELETE는 멱등하고 POST는 아니다. 재시도 설계의 기준이 된다.
- **상태 코드**
  - 2xx 성공 (200 OK, 201 Created, 204 No Content)
  - 3xx 리다이렉트 (301 영구, 302 임시, 304 Not Modified)
  - 4xx 클라이언트 잘못 (400 형식 오류, 401 인증 안 됨, 403 권한 없음, 404 없음, 429 요청 과다)
  - 5xx 서버 잘못 (500 내부 오류, 502 Bad Gateway, 503 일시 불가, 504 Gateway Timeout)
- **401과 403의 차이**: 401은 "누구인지 모르겠다", 403은 "누구인지는 알지만 안 된다".
- **502와 504의 차이**: 둘 다 프록시가 뒤쪽 서버 때문에 내는 오류다. 502는 뒤쪽이 이상한 응답을 줬거나 죽었을 때, 504는 뒤쪽이 제시간에 응답하지 않았을 때.

### HTTPS와 TLS

- TLS는 **암호화**(도청 방지), **무결성**(변조 방지), **인증**(상대가 진짜인지 확인)을 제공한다.
- 서버는 인증기관(CA)이 서명한 **인증서**를 제시하고, 클라이언트는 자신이 신뢰하는 CA 목록으로 검증한다.
- 고객사가 **사설 CA**나 **TLS 검사 프록시**를 쓰면 우리 프로그램이 인증서를 신뢰하지 못해 오류가 난다. 해결책은 검증을 끄는 것이 아니라 고객사 CA 인증서를 신뢰 목록에 추가하는 것이다.

### 프록시, 로드 밸런서, 방화벽

- **포워드 프록시**: 내부 사용자가 외부로 나갈 때 거치는 관문. 기업망에서 외부 API 호출이 막히는 흔한 이유다.
- **리버스 프록시**: 외부 요청을 받아 내부 서버로 넘겨 준다. (Nginx, API Gateway)
- **로드 밸런서**: 요청을 여러 서버에 나눠 준다. L4는 IP와 포트 기준, L7은 HTTP 내용(경로, 헤더) 기준.
- **방화벽**: 출발지, 목적지, 포트 기준으로 통신을 허용하거나 막는다. 들어오는 방향(인바운드)과 나가는 방향(아웃바운드)을 따로 본다.

### CORS

브라우저는 다른 출처(도메인, 포트, 프로토콜 중 하나라도 다름)로 보내는 요청의 응답을 기본적으로 차단한다. 서버가 `Access-Control-Allow-Origin` 헤더로 허용해야 한다.

- CORS는 **브라우저가 적용하는 규칙**이다. curl이나 서버 간 호출에서는 일어나지 않는다.
- "Postman에서는 되는데 웹에서는 안 된다"면 CORS를 먼저 의심한다.

## 현장에서 만나는 상황

### 상황 1: "API 호출이 안 돼요"

- **증상**: 우리 제품이 고객사 서버에서 외부 API를 호출하지 못한다.
- **확인 순서**
  1. 오류 메시지가 무엇인가: 이름 해석 실패, 연결 거부, 타임아웃, 인증서 오류, 4xx, 5xx 중 어느 것인가
  2. `dig 도메인` 또는 `nslookup` 으로 DNS가 풀리는가
  3. `curl -v https://도메인` 으로 어느 단계에서 멈추는가
  4. 회사 프록시 설정(`HTTPS_PROXY`)이 필요한가
  5. 방화벽 아웃바운드 허용 목록에 목적지가 있는가
- **오류별 해석**

| 오류 | 의미 | 의심할 곳 |
| --- | --- | --- |
| Could not resolve host | DNS 실패 | 사내 DNS, 오타 |
| Connection refused | 목적지에 도달했으나 해당 포트에 듣는 프로그램이 없음 | 서비스가 죽었거나 포트가 틀림 |
| Connection timed out | 응답 자체가 없음 | 방화벽이 조용히 버림, 라우팅 |
| certificate verify failed | 인증서를 신뢰할 수 없음 | 사설 CA, TLS 검사 프록시 |
| 407 | 프록시 인증 필요 | 프록시 계정 설정 |

- **고객에게 설명하는 말**: "저희 프로그램이 외부 서비스로 나가는 길이 회사 방화벽에서 막혀 있습니다. 보안팀에 이 주소와 443 포트의 외부 접속 허용을 요청해 주시면 됩니다."

### 상황 2: "가끔 느려요, 가끔 끊겨요"

- **확인 순서**: 특정 시간대인가, 특정 사용자인가, 특정 요청인가를 먼저 나눈다. 그다음 응답 시간을 구간별로 본다. `curl -w` 옵션으로 DNS, 연결, TLS, 첫 바이트까지의 시간을 따로 볼 수 있다.
- **흔한 원인**: 로드 밸런서의 유휴 연결 타임아웃이 애플리케이션보다 짧음, 커넥션 풀 고갈, 특정 서버만 불량, DNS 캐시 문제.

### 상황 3: "웹 화면에서만 오류가 나요"

- 브라우저 개발자 도구의 네트워크 탭과 콘솔을 본다. CORS 오류는 콘솔에 명시된다.
- 사전 요청(preflight, OPTIONS 메서드)이 실패하는지 확인한다. 프록시나 방화벽이 OPTIONS를 막는 경우가 있다.

## 면접 예상 질문

### Q. 브라우저에 URL을 입력하면 무슨 일이 일어나나요?

DNS로 도메인을 IP로 바꾸고, TCP 3-way handshake로 연결을 맺은 뒤, HTTPS라면 TLS 핸드셰이크로 인증서를 검증하고 키를 합의합니다. 그 위에서 HTTP 요청을 보내고 응답을 받아 브라우저가 HTML을 파싱하고 렌더링합니다. 이 순서를 아는 것이 중요한 이유는 장애가 났을 때 어느 단계에서 멈췄는지로 원인을 좁힐 수 있기 때문입니다.

### Q. 타임아웃과 Connection refused는 어떻게 다른가요?

Connection refused는 목적지 기기까지는 도달했지만 그 포트에서 듣고 있는 프로세스가 없어서 거절 응답이 돌아온 것입니다. 타임아웃은 아무 응답도 돌아오지 않은 것으로, 보통 방화벽이 패킷을 버리고 있거나 경로 자체가 없을 때 발생합니다. 그래서 refused면 서비스 상태를, 타임아웃이면 네트워크 정책을 먼저 봅니다.

### Q. CORS는 왜 있고 어떻게 해결하나요?

악성 사이트가 사용자의 브라우저를 이용해 다른 사이트의 데이터를 읽어 가는 것을 막기 위한 브라우저의 보안 정책입니다. 서버에서 허용할 출처를 응답 헤더로 지정해 해결합니다. 모든 출처를 허용하는 것은 피하고 필요한 출처만 명시합니다. 개발 환경에서는 프록시로 같은 출처처럼 보이게 하는 방법도 씁니다.

### Q. HTTP와 HTTPS의 차이는 무엇인가요?

HTTPS는 HTTP를 TLS 위에서 주고받는 것입니다. 통신 내용이 암호화되어 도청할 수 없고, 중간에 변조되면 알 수 있으며, 인증서로 상대 서버가 진짜인지 확인합니다.

### Q. 고객사에서 인증서 오류가 납니다. 검증을 끄면 안 되나요?

끄면 안 됩니다. 검증을 끄면 중간자 공격을 막을 수 없게 됩니다. 기업 환경에서 이 오류는 대부분 사설 CA나 TLS 검사 프록시 때문이므로, 고객사 CA 인증서를 받아 신뢰 저장소에 추가하는 것이 올바른 해결입니다.
