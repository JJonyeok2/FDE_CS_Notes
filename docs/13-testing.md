# 13. 테스트

> 한 줄 요약: 고객 환경에 배포한 코드는 고치러 가기도 어렵다. 무엇을 어떻게 테스트해야 안심하고 바꿀 수 있는지 알아야 한다.

## 개념 요약

### 왜 테스트하는가

- **바꿀 수 있는 자신감**: 기존 기능을 깨지 않았는지 바로 확인한다.
- **문서 역할**: 테스트는 이 코드가 어떻게 동작해야 하는지 보여 준다.
- **빠른 발견**: 고객이 발견하기 전에, 배포하기 전에 잡는다.

### 테스트 종류

| 종류 | 무엇을 | 속도 | 예 |
| --- | --- | --- | --- |
| 단위 테스트 | 함수나 클래스 하나 | 매우 빠름 | 날짜 변환 함수가 올바른 값을 내는가 |
| 통합 테스트 | 여러 부품의 연결 | 중간 | API가 DB에 제대로 저장하고 읽는가 |
| E2E 테스트 | 사용자 관점의 전체 흐름 | 느림 | 로그인 후 주문까지 화면에서 완료되는가 |

### 테스트 피라미드

- 아래(단위)를 많이, 위(E2E)를 적게 둔다.
- 단위 테스트는 빠르고 실패 위치가 정확하다. E2E는 실제와 가깝지만 느리고 자주 깨진다.
- 반대 모양(E2E가 대부분)이 되면 테스트가 느리고 불안정해져 아무도 돌리지 않게 된다.

### 좋은 테스트의 조건

- **빠르다**: 느리면 안 돌린다.
- **독립적이다**: 순서와 상관없이 각자 통과한다. 서로 데이터를 공유하지 않는다.
- **반복 가능하다**: 언제 돌려도 결과가 같다. 현재 시각, 난수, 네트워크에 의존하지 않는다.
- **실패 이유가 분명하다**: 이름과 메시지만 보고 무엇이 깨졌는지 안다.
- **동작을 검사한다**: 내부 구현이 아니라 입력과 출력, 결과를 본다. 그래야 리팩터링해도 깨지지 않는다.

### 테스트 구조: AAA

```python
def test_주문_합계는_할인을_반영한다():
    # Arrange: 준비
    order = Order(items=[Item(price=10000, qty=2)], discount_rate=0.1)

    # Act: 실행
    total = order.total()

    # Assert: 확인
    assert total == 18000
```

### 무엇을 테스트하나

- **핵심 업무 규칙**: 금액 계산, 권한 판단, 상태 전이
- **경계값**: 0, 빈 목록, 최댓값, 날짜 경계(월말, 윤년, 자정)
- **예외 입력**: NULL, 잘못된 형식, 중복
- **과거에 터졌던 버그**: 버그를 고칠 때 그 버그를 재현하는 테스트를 먼저 쓴다(회귀 테스트)
- 단순한 게터, 프레임워크 자체 기능은 테스트하지 않아도 된다.

### 테스트 대역

외부 의존성(DB, 외부 API, 현재 시각)을 가짜로 바꿔 빠르고 반복 가능하게 만든다.

| 이름 | 역할 |
| --- | --- |
| 스텁 | 정해진 값을 돌려준다 |
| 목 | 어떻게 호출되었는지 기록하고 검사한다 |
| 페이크 | 간단하게 동작하는 대체 구현 (메모리 DB) |

- 너무 많이 가짜로 바꾸면 테스트는 통과하는데 실제로는 안 되는 상황이 생긴다. 통합 테스트로 보완한다.
- 통합 테스트에서는 실제 DB를 컨테이너로 띄워 쓰는 방식(Testcontainers 등)이 흔하다.

### 커버리지

- 테스트가 코드의 몇 퍼센트를 실행했는지 나타낸다.
- 높은 커버리지가 좋은 테스트를 뜻하지 않는다. 실행만 하고 검사하지 않을 수 있다.
- 커버리지는 **테스트하지 않은 곳을 찾는 도구**로 쓴다. 목표 수치로 쓰면 의미 없는 테스트가 늘어난다.

### TDD

테스트를 먼저 쓰고(실패), 통과할 만큼만 구현하고, 정리한다(빨강 → 초록 → 리팩터). 요구 사항이 분명한 로직에 특히 효과적이다.

### CI에서 돌리기

- 코드를 올릴 때마다 자동으로 테스트를 돌린다.
- 테스트가 실패하면 병합하지 못하게 막는다.
- 가끔 실패하는 불안정한 테스트(flaky test)는 방치하지 않는다. 사람들이 실패를 무시하는 습관이 생긴다.

### LLM 기능은 어떻게 테스트하나

LLM의 출력은 매번 달라질 수 있어 일반적인 `assert` 로는 검사하기 어렵다.

- **결정적인 부분은 일반 테스트로**: 프롬프트 조립, 출력 파싱, 검증, 재시도 로직.
- **LLM 호출은 대역으로**: 단위 테스트에서는 정해진 응답을 돌려주는 가짜로 바꾼다.
- **형식 검사**: 출력이 JSON 스키마를 지키는가, 필수 필드가 있는가.
- **평가 세트**: 품질은 [LLM 응용](./09-llm-application#평가)의 평가 방식으로 측정한다. 프롬프트나 모델을 바꿀 때 CI에서 돌려 점수가 떨어지면 알린다.

### 도구

| 언어 | 단위와 통합 | E2E |
| --- | --- | --- |
| Python | pytest, unittest.mock | Playwright |
| JavaScript, TypeScript | Jest, Vitest, Testing Library | Playwright, Cypress |
| React Native | Jest, React Native Testing Library | Detox, Maestro |

## 현장에서 만나는 상황

### 상황 1: 테스트가 없는 고객사 코드를 고쳐야 한다

- 바꾸기 전에 **현재 동작을 고정하는 테스트**(특성 테스트)를 먼저 쓴다. 맞는 동작인지와 상관없이 지금 어떻게 동작하는지를 기록한다.
- 그다음 고친다. 의도하지 않은 변화가 있으면 테스트가 알려 준다.

### 상황 2: 고객 데이터에서만 터지는 버그

- 문제를 일으킨 입력을 찾아 개인정보를 가린 뒤 테스트 데이터로 만든다.
- 회귀 테스트로 남겨 같은 문제가 다시 생기지 않게 한다.

### 상황 3: E2E 테스트가 자꾸 깨진다

- 고정된 시간만큼 기다리는 코드가 원인인 경우가 많다. 요소가 나타날 때까지 기다리는 방식으로 바꾼다.
- 화면 문구나 CSS 클래스 대신 테스트 전용 식별자(`data-testid`)로 요소를 찾는다.
- E2E에서 검사하는 것을 핵심 흐름 몇 개로 줄이고 나머지는 아래 단계로 내린다.

### 상황 4: "테스트 짤 시간이 없어요"

- 전부가 아니라 위험이 큰 곳부터 쓴다. 돈 계산, 권한, 데이터 변환.
- 버그를 고칠 때마다 그 버그의 테스트 하나씩만 추가해도 쌓인다.

## 면접 예상 질문

### Q. 단위 테스트와 통합 테스트의 차이는 무엇인가요?

단위 테스트는 함수나 클래스 하나를 외부 의존성 없이 검사해 빠르고 실패 위치가 정확합니다. 통합 테스트는 DB나 외부 API 같은 여러 부품이 실제로 함께 동작하는지 검사합니다. 단위 테스트를 많이 두고, 연결 지점은 통합 테스트로 확인하는 구성이 일반적입니다.

### Q. 목(mock)은 언제 쓰고 단점은 무엇인가요?

외부 API나 DB처럼 느리거나 결과가 바뀌는 의존성을 대신해 테스트를 빠르고 반복 가능하게 만들 때 씁니다. 너무 많이 쓰면 실제 연결은 깨졌는데 테스트는 통과하는 상황이 생기고, 내부 구현에 묶여 리팩터링할 때마다 테스트가 깨집니다. 그래서 핵심 연결은 통합 테스트로 보완합니다.

### Q. 테스트 커버리지는 높을수록 좋은가요?

높다고 좋은 테스트인 것은 아닙니다. 코드를 실행만 하고 결과를 검사하지 않아도 커버리지는 올라갑니다. 커버리지는 테스트가 빠진 위험한 곳을 찾는 데 쓰고, 핵심 업무 규칙과 경계값을 제대로 검사하는지가 더 중요합니다.

### Q. LLM을 쓰는 기능은 어떻게 테스트하나요?

출력이 매번 달라질 수 있으므로 결정적인 부분과 품질을 나눕니다. 프롬프트 조립, 출력 파싱과 검증, 재시도 같은 로직은 LLM 호출을 대역으로 바꿔 일반 테스트로 검사합니다. 답변 품질은 평가 세트를 만들어 점수로 측정하고, 프롬프트나 모델을 바꿀 때 점수가 떨어지는지 확인합니다.

### Q. 테스트 코드를 작성해 본 경험이 있나요?

있는 그대로 답한다. 직접 작성한 경험이 적다면 써 본 도구(예: Playwright)와 무엇을 확인했는지, 그리고 지금이라면 어디에 어떤 테스트를 넣겠는지를 내 프로젝트 기준으로 구체적으로 말한다. 꾸며 낸 경험은 꼬리 질문에서 드러난다.
