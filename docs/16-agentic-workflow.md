# 16. Agentic Workflow와 멀티 에이전트 시스템

> 한 줄 요약: 고객은 "AI 에이전트"를 원한다고 말하지만, 실제로 필요한 것은 대부분 잘 설계된 워크플로다. 언제 고정된 흐름을 쓰고 언제 모델에게 판단을 맡길지, 에이전트를 여러 개로 나누는 것이 언제 이득인지를 판단할 수 있어야 한다.

## 개념 요약

### 용어 정리

| 용어 | 의미 |
| --- | --- |
| 워크플로 | LLM과 도구가 **미리 정해진 순서**로 실행된다. 경로를 코드가 정한다 |
| 에이전트 | LLM이 **스스로 다음 행동을 정하며** 목표를 향해 반복한다. 경로를 모델이 정한다 |
| Agentic Workflow | 워크플로 안의 일부 단계에서 모델이 판단하고 도구를 쓰는 구조. 둘 사이의 넓은 스펙트럼을 가리킨다 |
| 멀티 에이전트 | 역할이 다른 여러 에이전트가 나눠서 일하고 결과를 주고받는 구조 |

자율성은 0 아니면 1이 아니라 **조절하는 값**이다. 단순한 것부터 시작해 필요할 때만 자율성을 늘린다.

### 워크플로 패턴

| 패턴 | 구조 | 예 |
| --- | --- | --- |
| 프롬프트 체이닝 | 한 단계의 출력이 다음 단계의 입력. 중간에 검사 단계를 넣을 수 있다 | 초안 작성 → 형식 검사 → 번역 |
| 라우팅 | 입력을 분류해서 맞는 처리 경로로 보낸다 | 문의를 환불, 기술 지원, 일반 문의로 나눠 각각 다른 프롬프트로 |
| 병렬화 | 여러 작업을 동시에 돌리고 합친다. 나눠서 하기 또는 여러 번 해서 투표 | 계약서의 조항별 검토를 동시에, 위험 판단을 세 번 해서 다수결 |
| 오케스트레이터와 작업자 | 중심 모델이 작업을 나눠 작업자에게 맡기고 결과를 종합한다. 나누는 방법을 미리 알 수 없을 때 | 여러 파일에 걸친 코드 수정, 여러 출처 조사 |
| 평가자와 개선자 | 한 모델이 만들고 다른 모델이 평가해 피드백하며 반복한다 | 번역 품질 개선, 검색 결과 보완 |

### 에이전트의 구성 요소

```
목표 → [ 생각 → 도구 선택 → 도구 실행 → 결과 관찰 ] 반복 → 완료 판단 → 결과
```

- **모델**: 판단하는 두뇌
- **도구**: 검색, DB 조회, API 호출, 코드 실행, 파일 읽기 쓰기. 모델에게는 이름, 설명, 인자 형식만 알려 주고 실제 실행은 우리 코드가 한다
- **지시(시스템 프롬프트)**: 역할, 목표, 제약, 언제 멈출지
- **메모리**
  - 단기: 현재 작업의 대화와 도구 결과 (컨텍스트 윈도 안)
  - 장기: 이전 작업에서 배운 것, 사용자 선호 (외부 저장소에 두고 필요할 때 꺼냄)
- **계획**: 큰 목표를 단계로 나누고, 진행하면서 고친다
- **종료 조건**: 목표 달성, 최대 반복 횟수, 비용 상한, 사람에게 넘기기

**ReAct**는 "생각하고(Reason) 행동하는(Act)" 것을 번갈아 하는 기본 패턴이다. 대부분의 에이전트가 이 형태다.

### 도구 설계가 성능을 좌우한다

- 도구 이름과 설명은 **모델이 읽는 문서**다. 사람에게 설명하듯 명확하게 쓴다. 언제 쓰고 언제 쓰지 않는지도 적는다.
- 인자를 단순하게 한다. 모델이 틀리기 쉬운 형식(복잡한 중첩 구조, 애매한 날짜 형식)을 피한다.
- 비슷한 도구가 여럿이면 모델이 헷갈린다. 줄이고 합친다.
- 도구의 결과는 모델이 다음 판단에 쓸 만큼만, 읽기 좋게 돌려준다. 거대한 JSON을 그대로 주지 않는다.
- 오류도 모델이 이해할 수 있는 말로 돌려준다. "날짜 형식이 틀렸습니다. YYYY-MM-DD로 다시 시도하세요."

### 사람의 개입

| 수준 | 내용 |
| --- | --- |
| 사람이 실행 | AI는 제안만 하고 사람이 실행 |
| 사람이 승인 | AI가 실행 직전에 멈추고 사람이 승인 |
| 사람이 감독 | AI가 실행하고 사람은 기록을 보고 필요하면 되돌림 |
| 완전 자동 | 사람 개입 없음 |

되돌릴 수 없는 행동(삭제, 송금, 외부 발송, 운영 시스템 쓰기)은 **승인** 단계를 기본으로 둔다. 신뢰가 쌓이면 범위를 넓힌다.

### 멀티 에이전트 시스템

**왜 나누는가**

- 한 에이전트에게 도구와 지시가 너무 많으면 성능이 떨어진다. 역할을 나누면 각자 좁고 명확한 지시와 적은 도구를 갖는다.
- 독립적인 일을 **병렬로** 처리할 수 있다.
- 각 에이전트가 **자기 컨텍스트**를 가져서, 긴 조사 결과를 요약만 넘겨줄 수 있다.

**구조**

| 구조 | 설명 | 특징 |
| --- | --- | --- |
| 순차(파이프라인) | 정해진 순서로 넘김 | 단순, 예측 가능. 사실상 워크플로 |
| 감독자(Supervisor) | 중심 에이전트가 하위 에이전트에게 일을 배분하고 결과를 모음 | 가장 흔함. 감독자가 병목이 될 수 있음 |
| 계층형 | 감독자 아래에 또 감독자 | 큰 문제를 나눌 때. 복잡도 급증 |
| 네트워크(스웜) | 에이전트끼리 직접 일을 넘김(handoff) | 유연하지만 흐름 추적과 디버깅이 어려움 |

**언제 나누지 말아야 하는가**

- 일이 서로 강하게 얽혀 있어 계속 정보를 주고받아야 할 때. 넘길 때마다 맥락이 손실된다.
- 단일 에이전트로 아직 해 보지 않았을 때. 대부분 한 에이전트와 좋은 도구로 충분하다.
- 비용이 문제일 때. 에이전트가 늘면 토큰 사용량이 몇 배로 는다.

### 에이전트 간 통신과 표준 프로토콜

| 프로토콜 | 연결하는 것 | 한 줄 설명 |
| --- | --- | --- |
| MCP (Model Context Protocol) | 에이전트 ↔ 도구와 데이터 | 도구와 데이터 소스를 표준 방식으로 노출해, 어떤 AI 애플리케이션에서든 같은 방식으로 붙여 쓰게 한다 |
| A2A (Agent2Agent) | 에이전트 ↔ 에이전트 | 서로 다른 회사나 프레임워크로 만든 에이전트가 자신의 능력을 알리고 작업을 주고받게 한다 |

비유하면 MCP는 에이전트가 쓰는 **공구의 규격**이고, A2A는 에이전트끼리 **일을 맡기는 방법**이다. 둘은 경쟁이 아니라 보완 관계다.

FDE 관점: 고객의 사내 시스템을 MCP 서버로 감싸 두면, 고객이 쓰는 여러 AI 도구에서 같은 연동을 재사용할 수 있다.

### 자주 생기는 실패

| 실패 | 증상 | 대응 |
| --- | --- | --- |
| 무한 반복 | 같은 도구를 계속 부름 | 최대 반복 횟수, 같은 호출 반복 감지 |
| 잘못된 도구 선택 | 엉뚱한 도구를 부르거나 인자가 틀림 | 도구 설명 개선, 도구 수 줄이기 |
| 오류 누적 | 초반의 작은 실수가 뒤로 갈수록 커짐 | 중간 검증 단계, 단계 수 줄이기 |
| 맥락 손실 | 에이전트 사이에서 중요한 정보가 빠짐 | 넘길 정보의 형식을 정함 |
| 조기 종료 | 다 안 끝났는데 끝났다고 함 | 완료 조건을 명확히, 평가자 단계 |
| 비용 폭증 | 토큰 사용량이 예상의 몇 배 | 요청별 비용 기록, 상한 설정, 작은 모델 활용 |
| 프롬프트 인젝션 | 도구가 읽어 온 외부 내용의 지시를 따름 | 외부 내용은 데이터로 취급, 도구 권한 최소화 |

### 관측과 평가

- **트레이스**: 각 단계의 입력, 모델의 판단, 도구 호출과 결과, 소요 시간, 토큰을 모두 기록한다. 에이전트 디버깅은 트레이스 없이는 불가능하다.
- **최종 결과 평가**: 목표를 달성했는가.
- **과정 평가**: 불필요한 단계는 없었는가, 올바른 도구를 썼는가, 비용은 적절했는가.
- 같은 입력에도 경로가 달라질 수 있으므로 여러 번 돌려서 성공률로 본다.

## 현장에서 만나는 상황

### 상황 1: 고객이 "AI 에이전트를 도입하고 싶어요"라고 한다

1. 자동화하려는 업무를 단계별로 그려 본다.
2. 각 단계가 **매번 같은지**, **판단이 필요한지**를 표시한다.
3. 매번 같은 단계는 일반 코드나 워크플로로, 판단이 필요한 단계에만 LLM을 넣는다.
4. 대부분 "워크플로 + 일부 단계의 LLM 판단"으로 충분하다. 그래야 예측 가능하고, 디버깅이 쉽고, 비용이 낮다.
- **고객에게 설명하는 말**: "모든 걸 AI가 알아서 하게 하면 매번 다르게 움직여서 결과를 믿기 어렵습니다. 정해진 순서는 시스템이 지키고, 판단이 필요한 부분만 AI에게 맡기는 방식으로 하겠습니다."

### 상황 2: 에이전트가 시연에서는 되는데 실사용에서 자주 실패한다

- 트레이스를 열어 실패한 사례들이 **어느 단계에서** 갈라지는지 본다.
- 흔한 원인: 도구 설명이 애매함, 실제 데이터의 예외 케이스, 너무 긴 맥락, 단계가 너무 많음.
- 실패 사례를 평가 세트에 넣고, 고친 뒤 성공률을 다시 잰다.

### 상황 3: 멀티 에이전트로 만들었는데 단일 에이전트보다 나쁘다

- 에이전트 사이에 넘기는 정보가 부족하지 않은지 본다.
- 일이 실제로 나뉠 수 있는 성격인지 다시 본다. 아니라면 하나로 합친다.

### 상황 4: "에이전트가 실수로 데이터를 지우면 어떡하죠?"

- 도구 단위로 권한을 나눈다. 조회 도구와 변경 도구를 분리하고, 변경 도구에는 승인 단계를 둔다.
- 모든 변경을 기록하고 되돌릴 수 있게 한다.
- 운영 환경 전에 복제 환경에서 충분히 돌려 본다.

## 면접 예상 질문

### Q. 워크플로와 에이전트의 차이는 무엇인가요?

워크플로는 LLM과 도구가 코드로 미리 정해진 순서대로 실행되고, 에이전트는 LLM이 상황을 보고 다음 행동을 스스로 정하며 반복합니다. 워크플로는 예측 가능하고 비용이 낮으며, 에이전트는 경로를 미리 정할 수 없는 문제에 유연하게 대응합니다. 정해진 순서로 풀리는 일이면 워크플로를 먼저 씁니다.

### Q. 멀티 에이전트는 언제 쓰고 언제 쓰지 않나요?

한 에이전트에게 지시와 도구가 너무 많아 성능이 떨어지거나, 서로 독립적인 하위 작업을 병렬로 처리할 수 있을 때 씁니다. 반대로 작업이 서로 얽혀 정보를 계속 주고받아야 하면 넘길 때마다 맥락이 손실되고 비용만 늘어나므로 단일 에이전트가 낫습니다. 먼저 단일 에이전트로 시도하고 한계가 확인될 때 나눕니다.

### Q. 에이전트의 신뢰성을 어떻게 높이나요?

도구를 적고 명확하게 설계하고, 반복 횟수와 비용에 상한을 두고, 중간 결과를 검증하는 단계를 넣습니다. 되돌릴 수 없는 행동 앞에는 사람의 승인을 둡니다. 모든 단계를 트레이스로 기록하고, 실패 사례를 모은 평가 세트로 여러 번 돌려 성공률을 측정하면서 개선합니다.

### Q. MCP는 무엇이고 왜 필요한가요?

AI 애플리케이션이 외부 도구와 데이터 소스에 연결하는 방식을 표준화한 프로토콜입니다. 표준이 없으면 AI 도구마다 같은 연동을 따로 만들어야 하지만, 한 번 MCP 서버로 만들어 두면 이를 지원하는 여러 AI 애플리케이션에서 재사용할 수 있습니다.

### Q. MCP와 A2A는 어떻게 다른가요?

MCP는 에이전트가 도구와 데이터에 접근하는 방식을, A2A는 서로 다른 에이전트끼리 작업을 맡기고 결과를 주고받는 방식을 표준화합니다. 하나는 에이전트와 도구 사이, 다른 하나는 에이전트와 에이전트 사이의 규약이라 함께 쓸 수 있습니다.

### Q. 에이전트가 같은 도구를 계속 호출하며 멈추지 않습니다. 어떻게 하시겠습니까?

먼저 트레이스로 도구 결과가 무엇이었는지 확인합니다. 대개 도구가 모델이 이해하지 못하는 오류나 결과를 돌려줘서 같은 시도를 반복하는 경우입니다. 도구의 결과와 오류 메시지를 명확하게 고치고, 최대 반복 횟수와 동일 호출 반복 감지를 넣어 안전장치를 둡니다.

## 내 프로젝트와의 연결

> - AI 코딩 에이전트를 여러 역할로 나눠 쓰거나, 작업 단계(명세, 구현, 검증 등)를 정해 둔 경험이 있는가? 왜 그렇게 나눴고 무엇이 좋아졌는가?
